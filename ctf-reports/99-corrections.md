## 4. SIABench의 성격 명시

이전 보고서는 SIABench를 forensics 근거로 쓰면서 그 성격을 밝히지 않았습니다. SIABench는 **CTF 포렌식 벤치마크가 아니라 SOC 보안사고 분석 벤치마크**입니다. [포렌식 편](04-forensics.md)에서는 이 사실을 절 도입부에 명시하고, 인용마다 "SOC 사고 분석 과제에서"라는 단서를 유지했습니다.

## 7. 측정 / 해석 / 가설 분리

모든 문장에 다음 세 표기 중 하나를 붙였습니다.

- **[측정]** — 논문이 실제로 측정한 결과 (측정 조건 병기)
- **[해석]** — 논문 저자가 결과에 붙인 설명
- **[가설]** — 이 글의 제안 (미검증)

그리고 각 글 말미에 **"확정된 것과 아직 가설인 것"** 표를 넣어, 어느 주장이 어느 범위의 근거를 갖는지 한눈에 보이게 했습니다.

이전 보고서에서 결론처럼 쓰였으나 실제로는 가설인 항목들:

- 동일 예산에서 멀티 모델 병렬화가 유리하다
- Forensics의 세션 간 지식 축적 ROI가 카테고리 중 최상이다
- 상위 모델의 상세 추론 궤적을 하위 모델에 넘기면 강력한 CoT 스캐폴딩이 된다

**세 항목 모두 어느 논문도 측정하지 않았습니다.** 직접 A/B로 확인해야 할 설계 가설로 표시했습니다.

### 이 라운드에서 바뀐 판단

**1. "다른 팀의 실패 목록"을 우리 개선 목록으로 옮기면 안 됩니다.** BearcatCTF에서 미해결로 남은 이미지 2문제의 원인은 픽셀 단위 비전 도구의 부재였고, 웹의 XSS 전원 실패 원인은 브라우저 부재였습니다. **둘 다 CTF-OS 이미지에서는 이미 해결되어 있습니다**(zbar·stegseek·opencv, Playwright+Chromium). 이전 라운드는 이 사실을 대조하지 않고 실패 목록을 그대로 옮겼습니다.

**2. CTF-OS의 병목은 도구가 아니라 오케스트레이션입니다.** Dockerfile과 `AGENTS.md`를 직접 확인한 결과, Type A(도구·프롬프트 부재) 실패는 상당히 해결된 상태이고 Type B(계획·상태 관리)는 전혀 손대지 않은 상태입니다. 설계도의 무게중심을 여기에 맞췄습니다.

**3. 이 설계도의 성공 지표는 해결률이 아닙니다.** 이게 이 라운드에서 추가된 가장 중요한 항목입니다(`R-EVL-5`, 원칙 6).

Second Look **[측정]**에서 아키텍처 세 변형(Executor / +Evaluator / +Planner)이 모두 19/30이었습니다. 정교화가 천장을 올리지 못했습니다. 오른 것은 3/3 성공 12→16, 스텝 −24%, 비용 −34%였습니다. **이 설계도가 제안하는 것은 전부 정교화이므로, 해결률로 평가하면 실패로 나옵니다.** 지표를 `consistency`·`cost_per_solve`·대회시간당 착지 수로 고정했고, 반대로 지식·인식 계층의 개선은 해결률로 보게 분리했습니다.

**4. 실행 형태의 전제가 일부 해소됐습니다.** 첫 판에서 "가장 취약한 전제"로 지목한 것은 "프롬프트로 주입한 규약이 Codex에서 준수되는지 모른다"였습니다.

로컬 `codex-cli 0.145.0`을 직접 확인한 결과 `PreToolUse` 훅이 도구 호출을 **차단하거나 재작성**할 수 있습니다. 즉 준수율을 측정해서 대응하는 게 아니라 강제할 수 있습니다. `X-18`을 "준수율 측정"에서 **"훅 강제 vs 프롬프트 주입 비교"**로 바꿨습니다.

반대로 새로 드러난 제약도 있습니다. `--output-schema`는 매뉴얼 문구가 *request*이고 검증·재시도 서술이 없으므로 **스키마 검증기를 우리가 만들어야 합니다.** 그리고 토큰·비용 상한이 CLI에 없어(`token_budget`이 `under development`) 예산 집행을 `turn.completed.usage` 누적으로 해야 합니다. 이 제약의 부수 효과가 좋습니다 — 거부 로그와 비용 곡선이 같은 이벤트 스트림에서 나오므로 **계측이 별도 단계에서 사라졌습니다.**

**5. 부정을 주장하기 전에 한 번 더 확인해야 합니다.** 검증 중에 `.codex/agents/*.toml`이 존재하지 않는다고 결론 낼 뻔했습니다. 매뉴얼의 서브에이전트 절만 읽으면 "모델이 알아서 delegate한다"로 보여 선언적 정의가 없는 것처럼 읽히는데, 별도 절에 커스텀 에이전트 파일 스키마가 있습니다. **실재를 확인하는 것보다 부재를 확인하는 것이 어렵습니다.**

## 10. 2026-07-28 라운드: 대회 계층 폐기와 엔진 단위 재정의

### 왜 뒤집었는가

9절이 대회 계층을 추가하면서 스스로 적어둔 문장이 근거가 됐습니다. **"직접 측정한 연구를 찾지 못했습니다."** `R-CON-*` 아홉 개 중 측정 기반은 넷이었고, 특히 `R-CON-5`(순위 정책)는 Excalibur가 "난이도 추정 능력이 없다"고 측정한 것에서 역으로 끌어낸 회피 설계였습니다.

이전 라운드는 그 공백을 `X-20` 하나로 판정하겠다고 했습니다. 이번 라운드의 판단은 다릅니다. **근거 없는 기능은 실험으로 정당화하는 것이 아니라 만들지 않는 것**이 이 시리즈의 원칙(안티-레버 절)에 더 맞습니다. 항이 일곱 개인 우선순위 공식은 가중치를 정할 데이터가 없고, 잘못 튜닝되면 FIFO보다도 사람의 판단보다도 나쁩니다.

대신 실제 요구가 무엇인지 다시 봤더니 훨씬 작았습니다. 필요한 것은 "엔진이 문제를 골라주는 것"이 아니라 **"사람이 문제를 하나 더 열고 싶을 때 자유롭게 열리는 것"**이었습니다. 그 요구는 스케줄러가 아니라 자원 리스 하나로 충족됩니다.

### 이 라운드에서 바뀐 판단

**1. 근거가 없는 자리는 실험이 아니라 공백으로 둡니다.** 이전 라운드는 근거 없는 대회 계층을 만들고 `X-20`으로 판정하기로 했습니다. 그런데 실험은 만든 것을 유지할지 정할 뿐, **만들지 않는 선택지를 되돌려주지 않습니다.** 안티-레버 절의 원칙을 설계도 자신에게 적용하지 않았던 셈입니다.

**2. 사람을 설계에서 지우지 않습니다.** "무엇을 먼저 풀지"는 사람이 이미 잘하고, 코드로 옮기면 비싸고 나쁩니다. 엔진이 맡아야 할 것은 사람이 못 하는 쪽입니다 — 관찰을 잃지 않고, 반증하고, 재현하고, 세션이 죽어도 이어가는 것.

**3. "여러 문제를 병렬로"는 정직하지 않은 광고였습니다.** 모델 슬롯이 전역 4개인데 wave 하나가 그것을 다 쓰면, 실제로 일어나는 일은 병렬이 아니라 시분할입니다. 09에서 동시성을 층으로 나눠 다시 적었습니다. 가장 큰 실효 병렬성은 모델 층이 아니라 **tool 층**에서 나옵니다 — 디컴파일과 메모리 분석은 수십 분씩 모델 슬롯을 전혀 쓰지 않습니다.

**4. 강제할 수 없는 것을 완료 조건에 쓰지 않습니다.** "전체 모델 슬롯 4 이하"는 Ultra의 내부 자동 위임을 관측할 수 없으므로 검증할 수 없습니다. 검증 불가능한 조건은 통과했다고 거짓말하거나 영원히 미달로 남습니다. 강제 가능한 것과 관측만 가능한 것을 분리했습니다.

### 라운드 중 정정: 모델 슬롯을 문제 단위로 내림

이 라운드 안에서 한 번 더 뒤집은 것이 있습니다. 위 판단들을 반영한 첫 판은 **worker 슬롯 3개를 전역 풀로 두고 세션들이 나눠 쓰게** 했습니다. 이건 요구사항 위반이었습니다.

요구사항은 "한 문제를 풀로 풀고, 다른 문제도 풀라고 명령했을 때 다른 세션에서 이 시스템이 온전히 똑같이 돌아가는 것"입니다. 슬롯을 나눠 주면 두 번째 세션은 축소판이 되고, 문서가 스스로 "두 번째 세션은 축소판이 아니다"라고 써 둔 문장과 충돌합니다.

**근거를 다시 보니 전역 풀로 묶을 이유가 없었습니다.** 모델 호출은 네트워크와 API를 쓸 뿐 호스트의 CPU·RAM·GPU를 거의 쓰지 않습니다. 6코어 27GiB라는 물리적 제약이 묶는 것은 **도구 실행**이지 모델 호출이 아닙니다. `model_slots = 4`는 호스트 용량이 아니라 Codex 계정 쪽 추정값이었고, 그것을 호스트 자원처럼 취급해 배분한 것이 오류였습니다.

| 항목 | 정정 전 | 이 라운드 정정 후 | 현재 as-built |
| --- | --- | --- | --- |
| worker 슬롯 | 전역 3개를 세션들이 선착순 분배 | **문제마다 3개.** 세션 둘이면 6, 셋이면 9 | 문제마다 세 논리 역할을 유지 |
| `captain_slot_cost` | 기본 2로 회계에 반영 | **삭제.** 모델 층 회계 자체를 없앰 | 역할 폭 계산에는 사용하지 않음 |
| `available_workers` 공식 | `clamp(model_slots − Σcaptain_cost, 0, worker_slots)` | **삭제** | provider 상한은 worker 수를 줄이지 않고 호출 시작만 기다리게 함 |
| 브로커의 중재 대상 | 모델 슬롯 + 도구 + GPU + remote | **도구 + GPU + remote만.** 모델 층은 브로커를 거치지 않음 | Batch `codex exec`에는 별도의 configurable cross-process FIFO provider limiter가 있음. Live native subcall은 이 local FIFO 밖 |
| 동시 모델 호출 수 | 예산으로 관리 | **관측·경고 전용.** 끊지 않음 | Batch는 설정 상한에서 FIFO 대기. Live native는 Codex/account/provider가 대기시킬 수 있음 |

이 라운드 직후에는 간섭 경로를 tool 예산 큐, GPU 순번, remote rate
limit의 셋으로만 적었다. **후속 구현에서 Batch provider FIFO가 네 번째
경로로 추가됐다.** 이 경로도 세션의 세 논리 역할이나 wave 폭을 줄이지
않고 실제 model call 시작만 늦춘다. Live native subcall은 CTF-OS local
FIFO 밖에 있으며 account/provider 대기 경계에 남는다.

같은 라운드에서 **Web 문제 두 개를 브로커가 거절한다는 규칙도 삭제**했습니다. rate limit이 묶는 것은 대회 서버로 나가는 **요청 수**인데, 그것을 "세션을 열지 못한다"로 잘못 번역한 것이었습니다. 세션을 여는 행위는 외부에 아무것도 보내지 않습니다. 제한은 요청 층에서 걸고, 세션은 거절하지 않습니다.

**두 오류의 형태가 같습니다.** 자원의 제약을 한 층 위인 세션의 제약으로 옮긴 것입니다. 제약은 그것이 실제로 존재하는 층에서만 걸어야 합니다.

   병목으로 측정되더라도 자동 순위·세션 전환을 도입하지 않는다. board의

   session UX를 개선하는 범위만 남긴다.
8. **Codex/account의 실제 quota는 여전히 자동 조회하지 못합니다.**
   현재 Batch `codex exec`는 configurable cross-process FIFO 전역 상한에서
   대기하고, Live native subcall은 CTF-OS local FIFO 밖에서
   Codex/account/provider가 대기시킬 수 있다. 어느 쪽도 역할 수나 wave
   폭을 줄이지 않는다. 429·provider queue의 실제 동작과 구독 plan 상한은
   운영 계측 대상이며, 하드 실패가 확인돼도 논리 역할을 전역 풀로
   축소하지 않는다.
