# 당신의 AI Agent가 CTF 문제를 못 푸는 이유 — 리버싱 편

> 이 글의 “CTF-OS 현황”은 연구 시작 시점의 역사적 baseline이다.
> 현재 구현 판정은 [10](10-implementation-result.md)과
> [12](12-final-acceptance.md)를 따른다.

리버싱은 이 시리즈에서 유일하게 **직관과 측정이 정면으로 충돌하는** 카테고리입니다.

우리는 보통 이렇게 생각합니다. LLM은 어셈블리보다 C 의사코드를 잘 읽으니까 디컴파일러가 성능의 핵심일 것이다. 따라서 안티 디컴파일 보호를 걸면 Agent를 막을 수 있을 것이다.

2026년 NDSS BAR 워크숍에서 나온 측정 결과는 그 반대입니다. **디컴파일러를 빼도 성공률이 떨어지지 않았고, 어떤 문제에서는 오히려 올라갔습니다.**

이 글은 그 결과를 출발점으로, 리버싱에서 Agent가 실제로 어디서 무너지는지를 정리합니다.

> **인용 규칙**: **[측정]** = 논문이 실제로 측정한 결과(측정 조건 병기), **[해석]** = 논문 저자의 설명, **[가설]** = 이 글의 제안(미검증). 출처 등급은 **A** 동료평가 논문 / **B** arXiv 프리프린트 / **C** 운영 사례·블로그 / **D** 도구 저장소입니다.

## Agent가 리버싱 문제를 푸는 방식

Agent의 기본 전략은 사람 리버서의 분석 과정을 빠르게 반복하는 것입니다. 파일 형식과 보호 기법을 확인하고, `strings`, `readelf`, `objdump`, `radare2`, Ghidra, IDA로 정적 분석 결과를 모으고, 필요하면 GDB나 trace 도구를 붙입니다. 그리고 의심스러운 함수와 문자열을 기준으로 가설을 세운 뒤 solver나 keygen을 만들어 실제 바이너리에 넣어봅니다.

강점은 방향이 아니라 **속도와 반복**입니다. 사람이라면 디컴파일 결과를 읽고 solver를 한 번 짜본 뒤 잠깐 멈추지만, Agent는 입력을 바꿔가며 수십 번을 지치지 않고 돌립니다.

그래서 리버싱 벤치마크는 대부분 **설명이 아니라 산출물**을 채점합니다.

> **CrackMeBench**는 CrackMe 스타일 리버싱 과제에 대한 Agent 평가 벤치마크입니다. 자유 서술 대신 프로그램이 실제로 받아들이는 input, serial, artifact, keygen을 **실행 가능한 오라클**로 채점합니다. symbol 정보가 거의 없는 바이너리와 표준 리버싱 도구만 제공하며, Agent는 네트워크가 차단된 Linux Docker에서 문제를 풉니다. v0는 공개 CrackMe 8문제(보정용)와 C/Rust/Go 템플릿에서 생성한 12문제(본 채점용)로 구성됩니다 [2]. **(B)**

**[측정]** 세 모델, 문제당 5분 예산, 3회 채점 제출 조건에서 생성 문제 12개에 대한 pass@3은 GPT-5.5 11/12(92%), Claude Opus 4.7 7/12(58%), Kimi K2 5/12(42%)였습니다. 어려운 절반 6문제만 보면 각각 5/6, 2/6, 1/6으로 격차가 더 벌어집니다. 공개 보정 8문제에서는 3/8, 2/8, 1/8이었습니다 [2].

여기서 두 가지가 보입니다. 첫째, **5분 예산에서도 생성형 crackme의 상당수가 풀립니다.** 둘째, **공개 CrackMe 쪽 점수가 오히려 낮습니다.** 후자는 공개 문제가 더 어렵거나 형태가 더 다양하기 때문으로 보이며, "학습 데이터에 있으니 더 쉬울 것"이라는 예상과는 다릅니다.

## 디컴파일러를 빼도 성능이 떨어지지 않는다

이 글의 핵심입니다.

> **Towards LLM-Resistant Software Protection**은 Ricerca Security의 연구로, 분석 루프를 Observe–Comprehend–Plan(S1–S3)으로, 소프트웨어 보호 기법을 Concealment–Complication–Misdirection(M1–M3)으로 모델링하고, 2025년 CTF에서 수집한 리버싱 24문제에 세 개의 LLM Agent(Claude Code, Codex CLI, ChatGPT-5.2 Pro)를 붙여 실패 로그를 분석한 연구입니다. Ubuntu 24.04 컨테이너에 표준 리버싱 툴킷을 넣고, 문제당 최대 3회 시도(성공 시 조기 중단), 네트워크 허용, write-up 접근이 확인된 실행은 제외했습니다 [1]. **(A, NDSS BAR 2026)**

**[측정]** 디컴파일러 유무에 따른 24문제 해결 수는 다음과 같습니다 [1].

| 에이전트 | 디컴파일러 있음 | 디컴파일러 없음 |
| --- | --- | --- |
| Claude Code (CC) | 15/24 (63%) | **17/24 (71%)** |
| Codex CLI (CX) | 14/24 (58%) | 14/24 (58%) |
| ChatGPT-5.2 Pro (CG) | 19/24 (79%) | (샌드박스 통제 불가로 비교 미실시) |

**[측정]** 24문제 중 20문제는 디컴파일러 유무와 무관하게 결과가 동일했습니다. 결과가 갈린 4문제 중 **3문제(#11, #21, #23)는 디컴파일러를 제거해야만 풀렸고**, 1문제(#16)만 디컴파일러를 빼자 못 풀게 됐습니다 [1].

**[해석]** 논문의 결론은 명확합니다. LLM Agent는 어셈블리에서 직접 추론하는 경우가 많고, 디컴파일러는 주로 **탐색(navigation)** 용도로 씁니다. 따라서 안티 디컴파일 방어는 LLM Agent에 대해 효과가 제한적입니다.

가장 인상적인 사례는 task #23입니다.

**[측정]** #23은 C++ 예외 처리기로 스택 머신을 구현한 프로그램으로, 실행을 이해하려면 레지스터와 스택 프레임 상태를 추적해야 합니다. 디컴파일러의 의사코드는 이 저수준 세부를 가려버렸고, Claude Code는 디컴파일러가 켜진 설정에서 실패했습니다. 디컴파일러를 빼자 어셈블리를 직접 분석해 성공했습니다 [1].

**즉 디컴파일 결과는 참고 자료일 뿐 아니라, 어떤 경우에는 적극적인 방해물입니다.** 의사코드는 원본 코드가 아니라 재구성이고, 저수준이거나 비표준적인 제어 흐름에서는 재구성 과정에서 정답에 필요한 정보가 사라집니다.

> **[가설]** 그렇다면 리버싱 Agent의 도구 구성은 "디컴파일러 우선, 필요하면 어셈블리"가 아니라 **"두 표현을 대등하게 두고, 불일치가 감지되면 어셈블리를 신뢰"**하는 쪽이 나을 수 있습니다. 다만 이 논문은 디컴파일러 유무 두 조건만 비교했을 뿐, "둘 다 주고 교차 검증시키기"라는 세 번째 조건은 측정하지 않았습니다.

**이 결과의 범위도 명확히 해둘 필요가 있습니다.** 논문 스스로 외적 타당성의 한계로 (i) crackme 스타일 CTF 리버싱에 한정된 범위, (ii) 실제 소프트웨어보다 훨씬 작은 바이너리, (iii) 24문제 3개 에이전트라는 작은 규모를 명시합니다. 특히 **도구 출력이 컨텍스트 한계를 넘는 대형 바이너리에서는 다른 결과가 나올 수 있다**고 직접 언급하고 있습니다. 또한 문제당 최대 3회 시도이므로 통계적 신뢰구간은 넓습니다.

## 보호 기법은 다른 단계를 부순다

논문의 두 번째 기여는 **어떤 보호 기법이 분석 루프의 어느 단계를 부수는지**를 나눈 것입니다.

| 보호 유형 | 정의 | 주로 부수는 단계 | 유도되는 약점 |
| --- | --- | --- | --- |
| **M1 Concealment** | 정보 자체를 숨김 (패킹, 자기수정 코드, 안티 디버깅) | S1 Observe | W3 컨텍스트 한계(간접적) |
| **M2 Complication** | 구조를 복잡하게 만듦 (제어흐름 난독화, 코드 가상화) | S2 Comprehend | W1 학습 편향, W4 계획 고착 |
| **M3 Misdirection** | 그럴듯하지만 거짓인 단서 (디코이 함수, 가짜 심볼) | S2 Comprehend | W2 관측 과신, W4 계획 고착 |

각각을 로그에서 확인된 사례로 보면 이렇습니다.

### M1 Concealment — 대부분 우회하지만, 막히면 완전히 막힌다

**[측정]** 패킹이 걸린 task #9, #12에서 Agent들은 언패킹 이후 메모리를 덤프해 실제 실행되는 코드를 복구했습니다. 디버거를 탐지하면 종료되는 task #10에서는 체크 자체를 패치해 디버깅을 활성화했습니다. 반면 유저 공간에서 디버깅이 어려웠던 task #18에서는 루프를 반복해도 **어떤 Agent도 유효한 디버깅 전략을 찾지 못해 전부 실패**했습니다 [1].

**[해석]** Concealment는 대개 진행을 막지는 않지만 실패한 관측을 늘리고 계획 선택지를 좁혀 실행을 길게 만들고, 그 결과 컨텍스트 한계를 간접적으로 유발합니다. 다만 #18처럼 **Observe 단계를 지속적으로 실패시키는 기법은 분석 자체를 정지**시킬 수 있어, LLM Agent에 대해 특히 효과적인 보호입니다.

### M2 Complication — 익숙한 도구로 도망친다

**[측정]** 제어흐름 변환이 심한 task #22에서 Agent들은 어셈블리 직접 추론이 어려워지자 angr 심볼릭 실행이나 GDB 기반 동적 분석으로 옮겨갔습니다. 심볼릭 실행은 상태 공간 폭발에 자주 걸렸고, 일부 실행은 진전이 없는데도 같은 접근을 계속했습니다 [1].

**[해석]** 복잡화는 이해를 방해하면서 **W1(학습 편향)**을 끌어냅니다. 과제에 안 맞는데도 "표준적인" 방법을 고르게 만들고, 그 방법이 실패하면 **W4(계획 고착)**가 전환을 더 늦춥니다.

### M3 Misdirection — 가장 효율적인 공격

**[측정]** task #13은 검증 루틴이 XTEA 구조를 따르지만 상수와 키 재료는 TEA나 Salsa/ChaCha를 연상시키도록 심어져 있었습니다. 여러 실행이 TEA 또는 ChaCha20이라고 잘못 결론짓고 틀린 경로로 검증을 진행했습니다. task #11에서는 디컴파일 출력이 **실제로는 호출되지 않는 디코이 함수**가 입력 검증을 수행하는 것처럼 보이게 했고, 여러 Agent가 그 함수의 로직을 분석해 잘못된 "해답"을 도출했습니다 [1].

**[해석]** Misdirection은 정보를 줄이거나 복잡도를 늘리는 대신 **분석자를 틀린 해석 쪽으로 적극적으로 몰고 갑니다.** 모순되는 증거가 나와도 Agent는 초기의 오도된 단서를 붙들고 그 모순을 설명해내려는 경향을 보였습니다. 이게 W2(관측 과신)이고, 여기에 W4(계획 고착)가 겹치면 예산을 다 쓰고도 수렴하지 못합니다.

**세 유형 중 CTF 출제 관점에서 가장 비용 대비 효과가 큰 것은 M3입니다.** 코드를 무겁게 만들지 않고도 Agent를 통째로 틀린 방향으로 보낼 수 있기 때문입니다. task #11의 디코이 함수는 그 자체로는 몇 줄짜리 코드입니다.

## 네 가지 약점

논문이 실패 로그에서 추출한 약점은 다음 네 가지이고, 각각 루프의 특정 단계에 대응됩니다 [1].

| 약점 | 무엇인가 | 어느 단계에서 터지는가 |
| --- | --- | --- |
| **W1 Training bias** | 학습 데이터에 흔한 패턴(전형적 컴파일러 출력, 잘 알려진 암호 로직, 자주 쓰는 CTF 도구)에 과적합해, 낯선 표현이나 비표준 구현 앞에서 틀린 가설을 세움 | S2 Comprehend |
| **W2 Over-trust in observations** | 도구 출력이나 자기 중간 가설을 충분한 검증 없이 사실로 취급 | S3 Plan에서 잘못된 결정으로 발현 |
| **W3 Context limitation** | 긴 반복 실행에서 관측이 쌓이며 앞선 증거를 유지·재참조하지 못함 | S2 → S3 전이에서 붕괴 |
| **W4 Plan persistence** | S3에서 고른 비효율적이거나 틀린 계획에 고착되어, 반복된 실패 후에도 대안으로 전환하지 못함 | S3 Plan |

이 네 가지는 리버싱 고유의 문제가 아닙니다. **이 시리즈의 다른 카테고리에서도 이름만 바꿔 반복됩니다.** 크립토에서는 W1이 "공격 패러다임 오인"으로, 포렌식에서는 W3이 "질문 의존 연쇄"로, 웹에서는 W4가 "scholar-like enumeration"으로 나타납니다.

특히 W4에 대해서는 리버싱 밖에서 나온 별도의 근거가 있습니다.

> **Failing to Falsify**는 숨겨진 규칙을 맞히기 위해 숫자 세 개 조합을 제안하고 피드백을 받는 실험으로 11개 LLM의 확증 편향을 평가한 연구입니다. **[측정]** 반례를 찾도록 유도하자 평균 규칙 발견률이 42% → 56%로 올랐습니다 [11]. **(B)**

리버싱 실험이 아니므로 직접 근거는 아닙니다. 하지만 **"반증을 명시적으로 요구하면 개선된다"는 방향성**은 W4 대응 설계의 출발점이 됩니다.

> **[가설]** 리버싱 Agent에 "이 가설이 틀렸다면 무엇이 관찰되어야 하는가"를 매 단계 강제하는 반증 루프를 넣으면 W2와 W4가 함께 줄어들 수 있습니다. Failing to Falsify의 14%p 개선은 숫자 규칙 과제에서 나온 값이므로, 리버싱에서 같은 폭이 나온다는 보장은 없습니다.

## 설명은 맞는데 정답은 못 찾는 경우

리버싱에서 LLM은 "XOR 기반 검증으로 보입니다", "AES와 유사한 구조입니다" 같은 설명을 잘 만듭니다. 분석 자체는 맞을 수도 있습니다. 하지만 CTF에서 제출하는 것은 설명이 아니라 flag입니다.

이 격차를 정면으로 측정한 것이 CREBench입니다.

> **CREBench**는 48개 표준 암호 알고리즘과 3종의 취약한 키 사용 시나리오, 3단계 난이도를 조합해 432개 문제를 구성한 암호 바이너리 리버싱 벤치마크입니다. 각 문제는 CTF 리버싱 형태이며, 평가는 알고리즘 식별부터 정확한 입력 복구까지 4개 하위 과제로 나뉩니다 [13]. **(B)**

**[측정]** 8개 프론티어 LLM 평가에서 최고 성능인 GPT-5.4가 100점 만점에 64.03점을 기록했고, **문제의 59%에서 flag를 복구**했습니다. 같은 과제에 대한 인간 전문가 기준선은 92.19점입니다 [13].

**식별과 복구를 나눠 보는 것이 핵심입니다.** S-box나 라운드 상수처럼 익숙한 패턴이 보이면 모델은 알고리즘 이름을 잘 맞힙니다. 그러나 상수가 XOR로 숨겨져 있거나, 키가 여러 조각으로 나뉘어 있거나, PRNG state까지 추적해야 하면 복구 성공률은 크게 떨어집니다.

**[해석]** CREBench에서도 모델이 처음 떠올린 암호 알고리즘이나 검증 방식을 지나치게 오래 고수하는 모습이 나타났습니다. 앞서 본 W4와 같은 현상입니다.

CrackMeBench가 keygen을 요구하는 이유도 같은 맥락입니다. keygen은 특정 입력 하나를 맞히는 것이 아니라 **주어진 입력에 맞는 키를 생성하는 함수**를 만들어야 하고, 숨겨진 사용자 이름으로도 검증되므로 값을 하드코딩해서는 통과할 수 없습니다 [2].

> **[가설]** 리버싱 Agent의 출력은 항상 실행 가능한 산출물이어야 합니다. 후보 입력은 실제 바이너리에 넣고, solver나 keygen은 여러 테스트 케이스로 돌리고, runtime trace가 가설과 일치하는지 확인하는 것입니다. CrackMeBench와 CREBench의 설계 철학이 이 방향이지만, "산출물 강제가 성공률을 얼마나 올리는가"를 통제 실험으로 측정한 연구는 아직 없습니다.

## 사람이 이기는 곳과 Agent가 이기는 곳

이 논문에서 가장 흥미로운 부분입니다. 대회의 실제 인간 정답률과 Agent 결과를 비교했습니다.

**[측정]** 전반적으로 인간 정답률이 높은 문제일수록 Agent도 잘 풀었습니다. 사람에게 어려운 문제는 Agent에게도 어렵습니다 [1].

**그런데 예외가 뚜렷한 패턴을 이룹니다.**

### Agent가 이기는 곳: 잘 알려진 논리 퍼즐

**[측정]** task #15는 인간 정답률 2.1%였는데 모든 Agent가 풀었습니다. 같은 대회의 task #4는 인간 정답률 24%였습니다. task #9(6.5%)와 task #7(14%)에서도 같은 패턴이 나옵니다 [1].

**[측정]** Agent가 이긴 문제들을 수동 검토한 결과, task #15는 pipe puzzle, task #9는 Nurikabe, task #8은 Kakuro, task #24는 컬러 노노그램을 입력 검증 로직으로 구현한 것이었습니다. 모두 퍼즐 상태와 동작이 프로세스 간 통신이나 비트 연산 같은 비직관적 로직으로 인코딩돼 있어, **사람은 코드만 보고 원래 문제가 무엇인지 알아채기 어렵습니다** [1].

**[해석]** 바이너리가 잘 알려진 논리 퍼즐을 인코딩하고 있을 때, Agent는 학습된 예시에 대한 패턴 매칭으로 의도된 구조를 사람보다 쉽게 식별할 수 있습니다.

이건 CTF 출제자에게 직접적인 함의를 갖습니다. **"사람이 알아보기 어렵게 인코딩한 유명 퍼즐"은 Agent에게 오히려 쉬운 문제입니다.**

### 사람이 이기는 곳: 표준에서 벗어난 것

**[측정]** task #12(인간 정답률 3.5%)는 입력 검증용 WebAssembly 코드와, **opcode 값과 명령의 매핑을 뒤섞은** 오픈소스 WebAssembly 런타임 변형으로 구성됐습니다. 인간 풀이자는 상위 오픈소스 코드를 참조해 해당 dispatch/mapping 로직을 찾아냈지만, Agent들은 바이너리만으로 매핑을 분석하려 했고 표준 WebAssembly 가정에 의존해 실패했습니다 [1].

**[해석]** 사전 지식과 "표준적" 가정이 깨질 때, 사람은 외부 참조(원본 소스 등)를 찾아 검증하는 능력에서 우위를 유지합니다.

**[측정]** 논문은 방어 설계 방향도 이 결과에서 끌어냅니다. LLM Agent에 대한 견고성은 특정 기법보다 **알려진 약점(W1–W4)을 안정적으로 유발하는지**에 달려 있으며, 유망한 방향은 (i) 작은 마찰을 여러 개 더하기보다 반복 루프(S1–S3) 자체를 반복적으로 교란하는 것, (ii) 표준 사양이나 도구 가정에서 의도적으로 벗어나 **외부 정보 의존을 강제**하는 것입니다. 반면 안티 디컴파일 방어는 효과가 제한적입니다 [1].

## 이를 보완하는 연구와 도구

최근 도구들은 LLM 하나에 바이너리를 통째로 맡기지 않습니다. RE 도구가 추출한 정보를 구조화해 컨텍스트로 넣고, Agent가 세운 가설을 다시 도구로 검증하는 방향입니다. 크게 세 갈래입니다.

### 1) 기존 RE 환경에 LLM을 붙이는 방향

> **R2AI**는 radare2 shell 안에서 REPL, batch mode, ReAct mode를 쓸 수 있게 만든 LLM 플러그인입니다. Ollama 같은 로컬 모델과 상용 API를 모두 연결할 수 있습니다 [3]. **(D)**

> **ida-semray**는 분석 범위와 입력 형식을 선택하고 LLM 제안을 검토한 뒤 IDA에 적용할 수 있게 만든 플러그인입니다. 단일 함수, 전체 함수, 지정한 call depth 범위를 분석할 수 있고 디컴파일된 C와 raw assembly를 모두 지원합니다 [14]. **(D)**

> **Ghidra MCP 서버**는 200개 이상의 MCP 도구를 노출하며 라이브 디버거 연동, 배치 문서화, ASLR 인지 정적↔동적 주소 변환을 제공합니다 [15]. **(D)**

**세 도구 모두 성능 향상을 측정한 공개 데이터는 없습니다.** 다만 ida-semray가 "디컴파일된 C와 raw assembly를 모두 지원"하는 것은 앞서 본 RQ2 결과와 정합적입니다.

### 2) 학습으로 바이너리 분석에 특화시키는 방향

> **ReCopilot**은 프롬프트만 붙인 도구가 아니라 추가 사전학습(CPT), 지도 미세조정(SFT), 선호 최적화(DPO)를 거쳐 학습한 바이너리 분석 특화 모델입니다. 관련 컨텍스트를 구조화하기 위해 call graph와 variable data flow를 활용합니다. **[측정]** 함수명 복원과 변수 타입 추론 평가에서 기존 도구 및 LLM 대비 13% 높은 성능을 보고했습니다 [5]. **(B)**

call graph는 함수 사이의 호출 관계를, variable data flow는 값이 어떻게 이동하는지를 보여줍니다. 함수 이름 복원이나 변수 타입 추정은 독립 과제처럼 보이지만, 실제 결과는 **주변 호출 관계와 데이터 흐름을 얼마나 정확히 함께 제공하느냐**에 달라집니다. 이게 W3(컨텍스트 한계)에 대한 직접적인 대응입니다.

### 3) Agent가 분석 절차 자체를 주도하는 방향

> **Rikugan**은 외부 MCP 클라이언트 없이 IDA Pro나 Binary Ninja 프로세스 안에서 자체 agent loop를 실행하는 리버싱 Agent입니다. 스크립트 실행 전 사용자 허가를 받고 대상 바이너리는 직접 실행하지 않는다는 안전 경계를 둡니다 [4]. **(D)**

> **Kong**은 복원한 함수명, 타입, signature를 Ghidra 프로그램 DB에 반영하고 최종 분석 결과를 내보내는 리버싱 Agent입니다. 작은 함수부터 분석한 뒤 결과를 쌓아 전체 프로그램으로 범위를 넓히는 bottom-up 방식으로 컨텍스트 손실을 줄입니다 [12]. **(D)**

### 4) 근거를 검증하는 방향

> **Clue-Driven Reverse Engineering**은 전체 코드를 한꺼번에 요약시키는 대신 함수명, API 호출, 문자열처럼 가치가 높은 단서를 먼저 추출하고 planning·rewriting·evaluation을 거쳐 결과를 검증하는 흐름을 제안했습니다 [8]. **(C, Black Hat USA 2025 발표)**

> **Celebi-POC**는 그 evaluation 단계를 공개한 PoC입니다. `Ref Check`는 이름 제안 시 모델이 실제 단서를 보고 있는지 attention head를 분석하고, `Lie Detector`는 token 생성 확률에서 불확실성이 큰 답을 찾습니다 [9]. **(D)**

**이 방향이 W2(관측 과신)에 가장 직접적으로 대응합니다.** LLM의 설명을 그대로 받아들이지 않고 그 근거가 된 관측으로 되돌아가 확인하는 구조이기 때문입니다.

> **DecLLM**은 디컴파일 결과를 재컴파일 가능한 코드로 복원하는 방법입니다. 한 번에 완벽하게 복원할 것으로 기대하는 대신 컴파일 오류와 실행 결과를 피드백으로 주고 반복 수정합니다. **[측정]** C 벤치마크와 실제 바이너리에서 재컴파일 성공률의 **상한이 약 70%**였습니다. 원래 재컴파일 불가였던 디컴파일러 출력 100개 중 70개가 재컴파일 가능해졌다는 의미이며, **GPT-3.5와 GPT-4로 달성한 값**입니다. 복원 코드는 CodeQL 기반 취약점 분석에도 쓸 수 있었습니다 [6]. **(A, ISSTA 2025)**

**"약 70%"를 전형적 결과로 읽으면 과대평가입니다.** 상한이고, 2025년의 GPT-3.5/GPT-4 기준값입니다. 이 수정 내역은 [출처 검증 기록](08-verification-log.md)에 있습니다.

### 사람을 보조할 때는 이야기가 다르다

> **Decompiling the Synergy**는 전문가 24명과 초보자 24명이 두 개의 CTF형 문제를 푸는 과정을 전용 디컴파일러 플러그인으로 계측한 연구입니다. 총 6,586분의 분석 과정과 1,517번의 LLM 상호작용을 기록했습니다 [10]. **(A, NDSS 2026, DOI 10.14722/ndss.2026.240380)**

**[측정]** LLM 지원은 초보자의 프로그램 이해도를 크게 높였지만 **전문가의 전체 성과에는 거의 영향을 주지 않았습니다.** 일부 사용자 정의 함수에서는 전문가의 분석 시간이 오히려 늘었고, 잘못된 취약점 제안이 이후 분석을 방해하는 사례도 관찰됐습니다 [10].

> **[가설]** 이 결과를 Agent 설계에 옮기면, **자율 분석용 Agent와 분석가 보조용 Agent는 요구사항이 다릅니다.** 전자는 외부에서 검증 가능한 산출물이 필요하고, 후자는 판단 근거와 불확실성을 사람이 확인할 수 있는 인터페이스가 필요합니다. 잘못된 제안이 전문가의 시간을 늘렸다는 관찰이 이 구분의 근거입니다.

## 성공/실패 조건 정리

| 잘 푸는 조건 | 관찰되는 특징 | 왜 잘 맞는가 |
| --- | --- | --- |
| 신뢰할 수 있는 관측 | 문자열, 상수, 비교 루틴이 정적 분석에서 바로 보입니다 | 관측과 실제 실행 경로가 어긋나지 않습니다 |
| 짧은 컨텍스트 | 검증 로직이 한두 함수나 단순한 호출 관계에 모여 있습니다 | W3(컨텍스트 한계)에 걸리지 않습니다 |
| 빠른 검증 | 후보 입력이나 solver 결과를 바이너리에 바로 넣어볼 수 있습니다 | 틀린 가설을 빨리 버릴 수 있습니다 |
| 익숙한 패턴 | XOR, base64, 표준 crypto 상수 | 학습 분포와 일치합니다 |
| **잘 알려진 논리 퍼즐이 인코딩된 경우** | pipe puzzle, Nurikabe, Kakuro, 노노그램 | 인간 정답률 2.1% 문제를 모든 Agent가 풀었습니다 |
| 실행 가능한 산출물을 요구받는 경우 | password, keygen, patch, emulator | 설명에서 멈추지 않고 외부 검증이 성립합니다 |
| call graph, data flow가 함께 제공됨 | 구조화된 컨텍스트 | 흩어진 단서를 한 흐름으로 묶기 쉬워집니다 |

| 실패 조건 | 관찰되는 특징 | 필요한 보완 |
| --- | --- | --- |
| 관측이 지속적으로 차단됨 (M1) | 유저 공간에서 디버깅 전략을 못 찾아 전원 실패 | 동적 분석 경로 확보, 메모리 덤프, 언패킹 후 재관측 |
| 오도 단서 (M3) | XTEA 구조에 TEA/ChaCha 상수, 호출되지 않는 디코이 함수 | 실행 경로 확인을 해석보다 먼저, 근거-가설 분리 기록 |
| 구조 복잡화 (M2) | 심볼릭 실행 상태 폭발 후 같은 접근 반복 | 도구 선택 근거 명시, 진전 없는 접근의 중단 조건 |
| 디컴파일러 과신 | C++ 예외 기반 스택 머신에서 의사코드가 저수준 정보를 가림 | 어셈블리와 교차 확인, 불일치 시 어셈블리 우선 |
| 계획 고착 (W4) | 틀린 암호 알고리즘 가정을 끝까지 유지 | 반증 루프, 중단 조건, 대안 계획 강제 |
| 비표준 사양 | 뒤섞인 WebAssembly opcode 매핑 | 외부 참조(원본 소스) 검색을 절차로 포함 |
| 결과물 부재 | 설명은 그럴듯하나 password/keygen이 없음 | 실행 가능한 산출물과 실제 바이너리 검증 강제 |

## 엔진 설계 요구사항

리버싱은 이 시리즈에서 **A등급 근거가 가장 두꺼운** 카테고리입니다. 따라서 여기서 나온 요구사항은 다른 카테고리보다 강하게 채택할 수 있습니다. ID 정의는 [엔진 설계도](06-engine-blueprint.md), 실험은 [실험 백로그](07-experiment-backlog.md)에 있습니다.

| ID | 요구사항 | 이 글의 근거 | 상태 | CTF-OS 현황 |
| --- | --- | --- | --- | --- |
| **R-OBS-1** | 사실마다 `confidence`(executed / tool-inferred / model-claimed)와 재현 명령을 기록한다 | W2 관측 과신 **(A)** | 해석 → 설계 | 미구현. `state.json`의 facts 필드 (`facts.jsonl`은 09 §3.1에서 폐기) |
| **R-OBS-2** | `tool-inferred` 단독으로 결론을 내지 못한다. 해석 전에 실행 경로를 확인한다 | task #11 디코이 함수가 검증 루틴처럼 보였고 여러 Agent가 그 로직으로 틀린 해답을 냄 **[측정]** | 측정 기반 | 미구현. `stages/observe.py`의 provenance 게이트 |
| **R-OBS-3** | 디컴파일러와 어셈블리를 대등하게 두고, 불일치 시 어셈블리를 신뢰한다 | 15/24 → **17/24**, task #23에서 의사코드가 저수준 정보를 가림 **[측정]** | 측정 기반. 교차검증 조건은 미측정 | 도구는 있음, 정책 없음 (**`X-03`**) |
| **R-OBS-5** | 언패킹·안티디버깅 감지 시 재관측을 강제한다 | task #9·#12는 덤프로 복구, #10은 체크 패치, #18은 전원 실패 **[측정]** | 측정 기반 | 미구현 |
| **R-CTX-5** | call graph, data flow, xref를 구조화 컨텍스트로 제공한다 | ReCopilot 13% 개선 **[측정]**(함수명·타입 과제) | CTF 전이 미검증 | Ghidra 있음, 배치 추출 없음 |
| **R-ORC-1** | 결론은 실행 가능한 산출물로만 인정한다 | CrackMeBench 실행 오라클, keygen은 숨겨진 사용자 이름으로도 검증 **(B)** | 벤치마크 철학, 효과 미측정 | 미구현. Proof |
| **R-ORC-4** | 가설마다 반증 테스트를 등록하고 지지 증거보다 먼저 실행한다 | 42% → 56% **[측정, 도메인 밖]** | **[가설]** | 미구현 (**`X-04`**) |
| **R-ORC-6** | 산출물을 여러 테스트 케이스로 재실행하고, 실패 시 확정을 취소한다 | keygen 일반화 요구 **(B)** | 벤치마크 철학 | 미구현 |
| **R-KNW-5** | 비표준 사양 감지 시 외부 원본 소스 검색을 절차로 수행한다 | task #12 뒤섞인 WebAssembly opcode, 인간 3.5% 해결 / 전 Agent 실패 **[측정]** | 측정 기반 | 미구현. Codex Pool의 Librarian role |

**이 표에서 `X-03`이 특별합니다.** 논문은 디컴파일러 있음/없음 두 조건만 비교했고, "둘 다 주고 불일치 시 어셈블리 우선"이라는 세 번째 조건은 측정하지 않았습니다. 우리가 그 조건을 측정하면 이 시리즈에서 가장 독자적인 결과가 나올 수 있습니다.

**그리고 이 글의 요구사항 중 `R-OBS-1`과 `R-OBS-2`는 도구가 아니라 기록 규율입니다.** 리버싱 편의 결론이 "디컴파일러를 빼도 성능이 안 떨어진다"였다는 것을 기억하면, 리버싱에서 부족한 것은 도구가 아니라 **도구 출력을 어떻게 취급하는지에 대한 규칙**이라는 것이 분명해집니다. CTF-OS 이미지에는 Ghidra 12.1.2와 pwndbg와 angr가 이미 있습니다. 없는 것은 `confidence` 필드입니다.
