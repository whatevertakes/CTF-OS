## 5. 발견

### 5.1 시간의 64~94%는 실행이 아니라 모델 사고 시간이다 — 심각도 높음

**[측정, A]** run 사이 간격에서 실행 시간을 뺀 값(모델 추론 + 대기):

| 문제 | 경과 | 실행 | 사고/대기 | 중앙 간격 | p90 간격 |
| --- | ---: | ---: | ---: | ---: | ---: |
| APT-213 | 179분 | 65분 | **156분** | 9.9초 | 50.7초 |
| podnote | 159분 | 52분 | **132분** | 26.2초 | 254초 |
| Go Through Me | 156분 | 46분 | **128분** | 12.0초 | 124초 |
| One Instruction | 24분 | 1.9분 | **22.6분** | 6.2초 | 28.1초 |
| f l and ag | 11분 | 0.7분 | **10.4분** | 17.1초 | 77.5초 |

**[해석]** 병목은 도구도 컨테이너도 아니고 **모델의 직렬 추론**이다. 설계가 폭 3 wave를 고정한 이유가 정확히 이것인데, 그 wave가 0.4%만 돌았으므로 이 병목은 한 번도 완화되지 않았다.

**[측정, B]** 사람이 15:17:50에 *"아니 병렬로 하면 되잖아 우리 설계 한거 처럼"* 이라고 지적했고, **1시간 2분 뒤인 16:19:39에 유일한 3역할 wave가 실행됐다.** 즉 이 시스템의 병렬화는 자동으로 트리거되지 않았고, 사람이 화를 낸 뒤 한 번 돌았다.

**[측정, A]** 그 유일한 wave의 산출물도 비어 있다. `builder`는 `thread.started`/`turn.started` 2줄(101 bytes)만 남기고 아무 결과도 내지 않았고, `falsifier`와 `reproducer`는 `"summary":"...in progress"` 상태 stub만 반환했다.

**[해석]** wave는 "안 쓰였다"가 아니라 **한 번 써 봤더니 산출물이 나오지 않았다.** 채택되지 않은 이유가 여기 있을 가능성이 크다.

### 5.2 실험 평가 루프가 닫히지 않는다 — 심각도 높음

**[측정, A]** 실험 상태 분포:

| 문제 | registered | awaiting_evaluation | kept | dropped | failed |
| --- | ---: | ---: | ---: | ---: | ---: |
| APT-213 | 1 | **286** | 0 | 0 | 34 |
| Go Through Me | 1 | **148** | 0 | 0 | 8 |
| podnote | 2 | **63** | 0 | 0 | 31 |
| One Instruction | 3 | 31 | 51 | 1 | 4 |
| f l and ag | 1 | 11 | 4 | 0 | 7 |

**[측정, C]** 설계는 `06:456`에서 이렇게 못박았다: *"`keep_if`와 `drop_if`를 실행 전에 적게 하는 것이 핵심입니다. **사후에 기준을 정하면 어떤 결과든 가설을 지지하는 쪽으로 해석됩니다.**"*

**[측정, A]** 그런데 등록된 실험 688건 중 686건이 `E-operator-*` — 즉 명령을 실행하는 순간 자동 생성된 레코드다. 사전등록된 어댑터 시드 실험은 **10건**뿐이다.

**[해석]** 지금 구조에서 "실험"은 사전등록된 판정 가능한 가설 검증이 아니라 **실행한 명령에 붙는 영수증**이다. `keep_if`/`drop_if`는 자유 텍스트이고 매처가 없으며(`models.py:657-658`), 판정은 모델의 명시적 `agent.evaluate` 호출에만 의존하는데 그 호출이 전체 세션에서 1회 실행됐다. 사전등록 규율이 방지하려던 사후 합리화는 **전혀 방지되지 않고 있다.**

**[가설]** 평가율이 높았던 rev(58%)와 crypto(17%)가 각각 24분·11분에 풀렸고, 평가율 0%인 pwn·web·forensics가 156~179분 걸렸다. 다만 이건 **난이도 교란이 전혀 통제되지 않은 상관**이다. 인과 주장으로 쓰면 안 되고, 판정하려면 §7의 실험이 필요하다.

### 5.3 플래그 후보의 97~99%가 정규식 오탐이다 — 심각도 높음

**[측정, C]** 런타임 기본 패턴에 generic 규칙이 있다 (`config.py:74-77`): `\b[A-Za-z0-9_]{2,32}\{[^{}\r\n]{1,512}\}`

**[측정, A]** 이 패턴이 실제로 잡은 것들:

- APT-213: 126건 중 실제 제출 후보 1건. 나머지는 `body{color:#222;font:normal 13px/1.4 arial,sans-serif;margin:0}`, `disabled{color:#ccc;...}`, `u003d{docid}` 같은 CSS/JS 조각
- Go Through Me: 34건 중 1건. 나머지는 `return{file:!1,glob:!1,sortOrder:!1}` 같은 minified JS
- rev: `DH{%s}` (포맷 문자열), pwn: `DH{fake_flag}`, `DH{...}` (문제 파일 안의 더미)

**[측정, A]** APT-213의 컨텍스트 팩 137 KB 중 **"Candidate flags" 섹션이 32 KB(23%)**를 차지한다. 같은 파일에서 "Open hypotheses"는 11 bytes다.

**[해석]** 모델에게 전달되는 컨텍스트의 4분의 1이 CSS 조각이고, 가설은 사실상 0바이트다. 컨텍스트 예산이 **신호에서 잡음으로 역전**돼 있다.

**[측정, C]** 설계는 오탐 필터를 정규식 층에 두지 않고 상태 기계와 proof로 거르기로 했다(`09:1024-1036`). **[해석]** 그 판단 자체가 틀린 건 아니지만, 후보가 컨텍스트에 그대로 실려 나가는 한 상태 기계는 **제출은 막아도 토큰은 막지 못한다.**

### 5.4 proof 게이트가 실제 제출을 가르지 못했다 — 심각도 높음

**[측정, A]** 제출 5건 전체:

| 문제 | proof_passed | 결과 |
| --- | :---: | --- |
| One Instruction One Thread | ✅ true | 정답 |
| f l and ag | ✅ true | 정답 |
| podnote | ❌ false | **정답** |
| Go Through Me | ❌ false | **정답** |
| APT-213 | ❌ false | **오답** |

**[해석]** proof를 통과한 2건은 모두 정답이었지만, proof 없이 제출된 3건 중 2건도 정답이었다. 즉 **proof는 지금 제출의 전제조건이 아니라 선택 사항**이고, 실제로 오답을 걸러낸 사례는 0건이다. `AGENTS.md:17-18`의 "A flag-looking string is a candidate, not proof"는 문서에만 살아 있다.

### 5.5 증거가 4,096자에서 잘려 모델에 전달된다 — 심각도 중간

**[측정, A]** `result.json`의 `stdout_summary` 상한은 4,096자다.

| 문제 | 상한 도달 run | 비율 | 원본 stdout 최대 |
| --- | ---: | ---: | ---: |
| APT-213 | 73 / 317 | 23% | 251,834 bytes |
| One Instruction | 25 / 90 | 28% | 33,814 bytes |
| Go Through Me | 26 / 156 | 17% | 57,835 bytes |
| podnote | 13 / 93 | 14% | 36,803 bytes |

**[해석]** 5건 중 1건꼴로 모델은 잘린 앞부분만 보고 다음 판단을 한다. 원본은 artifact로 보존되지만, 모델이 그걸 다시 읽으려면 추가 턴이 필요하고 그 턴이 §5.1의 사고 시간을 늘린다. APT-213 인계서 §10.5가 같은 문제를 독립적으로 지적했다: *"긴 JSON/HTML 출력은 `stdout_summary`의 앞부분이 잘려 핵심 metadata를 놓치기 쉽다."*

### 5.6 도구 세션 소유권이 병렬 작업을 직렬화한다 — 심각도 중간

**[측정, B]** 세션 로그의 `another session already owns <challenge>` 발생 횟수:

| 문제 | 충돌 |
| --- | ---: |
| rev/One Instruction One Thread | 18 |
| forensics/APT-213 | 16 |
| pwn/podnote | 7 |
| crypto/f l and ag | 3 |
| web/Go Through Me | 2 |

**[측정, B]** 같은 기간 Codex CLI 자체 `spawn_agent`는 52회 호출됐다.

**[해석]** 실제 병렬화 수단은 CTF-OS의 wave가 아니라 **Codex CLI의 서브에이전트**였는데, 서브에이전트들이 하나의 challenge tool session을 두고 경합했다. APT-213 인계서 §10.3이 이 상황을 정확히 기술한다: *"root의 공개 메타데이터 probe가 challenge tool session을 점유하면 로컬 복구 subagent가 `another session already owns`로 막혔다."*

**[해석]** 읽기 전용 분석까지 쓰기와 같은 lock을 잡는 것이 원인이다. `09:920`의 R-ENV-7 "단일 writer" 계약은 쓰기에만 필요한데 읽기에도 적용됐다.

### 5.7 상태 파일 쓰기 증폭과 디스크 무회수 — 심각도 중간

**[측정, A/D]** `state.json`은 커밋마다 전체가 재작성되고 직전 판본이 `state.prev.json`으로 복사된다(`09:741-750`).

| 문제 | revision | 최종 state 크기 | 누적 쓰기(추정) |

| APT-213 | 986 | 1,989 KB | ~1,004 MB |
| Go Through Me | 476 | 995 KB | ~242 MB |
| One Instruction | 335 | 694 KB | ~119 MB |
| podnote | 289 | 516 KB | ~76 MB |

**[측정, A]** 디스크 15 GB 중 14.9 GB가 APT-213의 `artifacts/workspace` (E01 이미지 12.8 GB, pagefile 1.5 GB, MFT 132 MB).

**[측정, C]** 이건 알려진 갭이다. `README:838-842`가 명시한다: *"누적 `runs/` raw, contest `submissions.jsonl`과 전체 challenge tree에는 **별도 총량 quota나 retention/GC가 없습니다.**"* 2차 검토(`11:38`)도 디스크 증폭을 HIGH로 올렸다.

**[해석]** 크기 상한(16 MiB / 16,384 항목)은 문서화돼 있지만 **커밋당 전체 재작성 비용은 어느 문서에도 없다.** 문제 하나가 986 revision을 찍는 것이 정상 운용이라면, revision 수에 비례하는 O(state 크기) 쓰기는 설계 가정 밖이다.

### 5.8 사람이 같은 것을 반복해서 교정한다 — 심각도 높음

**[측정, B]** 5문제 세션에서 사람의 개입을 유형별로 묶으면 다섯 가지가 반복된다.

| 유형 | 실제 발화 | 반복된 문제 |
| --- | --- | --- |
| **도구 위치를 알려줌** | *"ctf-os:core ... 이 이미지를 활용해라"*, *"core 이미지 안에 있다"* | podnote, rev, crypto, pwn |
| **원격 엔드포인트 갱신** | *"nc host3.dreamhack.games 17472 원격 이걸로 변경해라"*, *"http://host3...:17796 이걸로 교체해라"* | podnote, web, pwn |
| **절차 준수 감시** | *"문제 풀이 시스템 잘 따르고 있지?"*, *"컨테이너 안에서 도구 활용해서 하고 있지"* | web, forensics |
| **가짜 후보 지적** | *"실플래그가 나왔어? DH{testtttt} 이거 말고"* | web |
| **병렬화 지시** | *"아니 병렬로 하면 되잖아 우리 설계 한거 처럼"* | web |

**[해석]** 다섯 유형 모두 **시스템이 스스로 알 수 있는 것**이다. 이미지 안에 무슨 도구가 있는지, 원격 주소가 죽었는지, 지금 절차의 어느 단계인지, 후보가 문제 파일에서 온 더미인지, 지금 직렬로 돌고 있는지 — 전부 기계가 판정 가능한 상태다. 사람이 이걸 말로 교정하고 있다는 것은 **관측 가능성이 사람의 눈에만 있고 시스템에는 없다**는 뜻이다.

**[측정, A]** 특히 도구 부재는 실패로 직접 이어졌다. exit 127로 죽은 run에서 없던 명령: `sqlite3` (APT-213, Go Through Me 양쪽), `magick` (APT-213).

## 6. 개선 제안 (우선순위 순)

우선순위는 **(관측된 비용) × (변경의 작음)** 으로 매겼다.

### P0 — 지금 잃고 있는 것을 되찾는 변경

1. **후보 오탐 억제.** 문제별 명시 포맷(`acsc\{[0-9A-F]{32}\}`, `DH\{...\}`)을 등록하면 generic `word{...}` 규칙을 끄고, `.js`/`.css`/HTML `<script>`·`<style>` 구간은 후보 추출에서 제외한다. run당 후보 상한과 noisy-source 억제를 둔다.
   → 예상 효과: 컨텍스트의 23% 회수, 사람의 "가짜 후보 지적" 개입 제거. **[가설]**
2. **컨텍스트 팩 예산 재배분.** 지금 `Confirmed observations` 51 KB + `Candidate flags` 32 KB 대 `Open hypotheses` 11 bytes다. 섹션별 상한을 두고, 잘라야 한다면 후보부터 자른다.
3. **`stdout_summary`를 head 잘라내기에서 구조화 요약으로.** MIME별 요약기(JSON은 키 스키마 + 크기, HTML은 title/status/길이, TSV는 헤더 + 행 수)와 정확한 raw 포인터를 함께 준다.
4. **proof를 제출 전 필수 게이트로.** 지금은 `proof_passed:false`로도 제출이 기록된다. `ctfos submit`이 proof 없는 후보에 대해 명시적 override 플래그를 요구하게 한다.

### P1 — 채택 실패를 고치는 변경

5. **wave가 왜 빈 산출물을 냈는지부터 규명.** 유일한 3역할 wave에서 builder가 101바이트만 남긴 원인을 찾기 전에는 wave 채택을 논할 수 없다. 이건 기능 추가가 아니라 **버그 조사**다.
6. **읽기 전용 동시 접근 허용.** tool session lock을 읽기/쓰기로 분리한다. 읽기 전용 스냅샷 마운트를 동시 허용하고 쓰기 제안만 직렬화한다. lease 대기 큐를 가시화한다.
7. **`ctfos checkpoint` / `pause --handoff`.** APT-213 인계서는 사람이 요청해서 마지막에 손으로 쓴 것이다. 확정 필드·기각된 후보·다음 명령·반복 금지 작업을 원자적으로 남기는 명령이 필요하다.
8. **세션 시작 시 환경 브리핑 자동 생성.** 이미지 안의 도구 목록, 등록된 원격 타깃과 그 생존 여부, 현재 goal/실험 상태를 세션 첫 컨텍스트에 넣는다. 사람 개입 5유형 중 3유형이 여기서 사라진다.

### P2 — 구조적 부채

9. **state.json 증분 커밋.** 전체 재작성 대신 append-only 이벤트 + 주기적 스냅샷. revision이 수백~천 단위로 가는 것이 정상 운용임이 측정됐으므로 O(전체 크기) 쓰기는 유지 불가.
10. **artifact retention/GC.** 12.8 GB E01을 문제 디렉터리에 무기한 보관하는 정책이 없다. TTL과 `ctfos gc`를 둔다.
11. **`ctfos remove-target` / TTL.** APT-213 인계서 §10.6이 지적한 그대로, 등록한 프록시 타깃을 지우는 명령이 없다.
12. **복합 플래그의 필드 단위 상태.** APT-213은 4필드 조합 하나가 오답 처리되어, 어느 필드가 틀렸는지 정본에 남지 않았다. 필드별 `known-good / likely / unresolved / disproved`가 필요하다.

## 8. 이 분석의 한계

**[측정]** 표본은 문제 5개, 대회 2개, 하루치다. 카테고리당 1문제이므로 **카테고리별 비교는 할 수 없다.** 난이도가 통제되지 않았으므로 §5.2의 평가율-소요시간 상관은 인과가 아니다.

**[측정]** 66%의 raw shell 작업이 정본 밖에 있으므로, `state.json` 기반 수치는 실제 작업량의 하한이다. 반대로 세션 로그 기반 수치(B등급)에는 도구 설명 텍스트나 코드 인용에서 온 문자열 일치가 섞일 수 있어 상한 성격이다.

**[측정]** `pwn/panopticon`은 진행 중이므로 모든 결론에서 제외했다. 표에 남긴 숫자는 참고용이다.
