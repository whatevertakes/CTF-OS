# 실험 백로그 — [가설]을 판정 가능한 형태로

[엔진 설계도](06-engine-blueprint.md)와 [구현 설계도](09-implementation-blueprint.md)의 요구사항 중 상당수가 **[가설]** 상태입니다. 이 문서는 그 가설들을 "돌리면 답이 나오는 실험"으로 바꿉니다.

이 문서가 따로 있는 이유가 있습니다. 설계 문서 안에 "이건 미검증"이라고 적어두는 것만으로는 아무 일도 일어나지 않습니다. 미검증 항목은 시간이 지나면 검증된 것처럼 유통되고, 그 위에 다음 결정이 쌓입니다. **가설을 실험 ID로 등록하고 기본값 결정을 그 실험에 묶어두면**, 검증 없이 기능이 확정되는 경로가 막힙니다.

> **인용 규칙**: **[측정]** = 논문이 실제로 측정한 결과(측정 조건 병기), **[해석]** = 논문 저자의 설명, **[가설]** = 이 시리즈의 제안(미검증). 출처 등급은 **A** 동료평가 논문 / **B** arXiv 프리프린트 / **C** 운영 사례·블로그 / **D** 도구 저장소입니다.

## 실험 설계의 공통 규칙

### 규칙 1. 총 예산을 고정한다

이 규칙 하나가 이 문서의 존재 이유 절반입니다.

ExploitGym의 합집합 239는 단일 최고 조합 157보다 큽니다. 그런데 239는 **여러 모델·에이전트·조건의 성공을 전부 합친 값이고, 투입된 총 연산량이 157을 낸 단일 실행보다 훨씬 큽니다.** 이것을 "앙상블이 낫다"로 읽으면 예산이 같을 때의 효율에 대해 아무것도 모르는 상태에서 결정을 내리는 것입니다.

그래서 모든 A/B는 **총 벽시계 시간 또는 총 비용을 고정**합니다. 조건 B가 더 많이 계산해서 이기는 것은 결과가 아닙니다.

### 규칙 2. 문제 집합을 먼저 고정하고 나중에 바꾸지 않는다

조건을 돌린 뒤 문제 집합을 조정하면 그 시점부터 측정이 아니라 튜닝입니다. 집합은 실험 시작 전에 확정하고 파일로 남깁니다.

### 규칙 3. 지표를 이진 성공률로만 두지 않는다

ExploitBench의 관찰이 근거입니다. 이진 판정은 병목을 감춥니다. 5문제를 풀었다는 정보만으로는 나머지에서 크래시조차 못 냈는지, 제어를 못 잡았는지 알 수 없습니다. 그래서 모든 실험의 주 지표에 **사다리 도달 단계**를 포함합니다.

### 규칙 4. 실패 원인 라벨을 붙인다

SIABench의 5분류(Question Dependency / Wrong Commands / Infinite Loop / Hallucination / Shallow Investigation)와 리버싱 편의 W1–W4를 합쳐 라벨 집합으로 씁니다. 라벨 분포가 바뀌지 않았다면 그 개선은 다른 것을 고친 것입니다.

### 규칙 5. 개선이 없으면 그 컴포넌트를 제거한다

Second Look의 측정이 근거입니다. 아키텍처를 정교하게 해도 최대 성능은 19/30에서 움직이지 않았습니다. **효과가 확인되지 않은 컴포넌트는 유지 비용만 남깁니다.**

단, 이 규칙에는 예외가 하나 있습니다. Second Look에서 아키텍처가 실제로 개선한 것은 **일관성(3/3 성공 12→16)과 비용(−34%)**이었습니다. 최대 성능이 안 올랐다는 이유로 제거하면 그 이득도 함께 버립니다. 그래서 판정 기준에 일관성과 비용을 항상 포함합니다.

### 규칙 6. 변경의 종류에 따라 주 지표를 바꾼다

같은 이유의 반대편입니다. **오케스트레이션 변경을 해결률로 평가하면 전부 실패로 나옵니다.**

| 변경의 종류 | 주 지표 | 근거 |
| --- | --- | --- |
| 대회 계층, 예산·배분, 상태 관리 (`R-CON-*`, `R-BGT-*`) | `consistency`, `cost_per_solve`, **총 착지 수** | 아키텍처 세 변형이 모두 19/30. 오른 것은 3/3 성공 12→16, 비용 −34% **[측정]** |
| 지식, 취약점 인식, 관측 능력 (`R-KNW-*`, `R-OBS-*`) | `solve@3`, 사다리 최상단 도달률 | 인식되면 83%(19/23)가 익스까지 성공 **[측정]**. 인식 실패 7문제는 어떤 아키텍처로도 시작 못 함 |
| 컨텍스트 계층 (`R-CTX-*`) | `cle_count` 먼저, 그 다음 `solve@3` | CLE는 다른 개선을 가리는 노이즈. 요약 계층으로 **0**이 됨 **[측정]** |

이것이 [엔진 설계도](06-engine-blueprint.md)의 `R-EVL-5`입니다.

## 평가 하네스

실험을 돌릴 판이 없으면 실험 목록은 의미가 없습니다.

### 문제 집합의 세 층

| 층 | 구성 | 용도 | 오염 위험 |
| --- | --- | --- | --- |
| **L1 회귀** | 이미 풀어본 문제 20~30개, 카테고리 균형 | 변경이 기존 능력을 깨뜨리지 않는지 확인. 빠르고 싸다 | 높음 (의도된 것) |
| **L2 보류** | 풀 수 있다고 확인했으나 세션 기록에서 격리한 문제 20~30개 | A/B 판정의 주 무대 | 중간 |
| **L3 Live** | 진행 중인 대회 | 최종 확인. write-up이 없다 | 낮음 |

**L2가 A/B의 주 무대인 이유**는 CTFusion의 측정에 있습니다. 동일한 모델·에이전트 조합에서 정적 벤치마크 성공률이 Live CTF의 약 2.2~2.4배였습니다. 연구진 스스로 이 결과를 *suggestive rather than conclusive*로 명시했고 난이도 차이와 오염의 기여도를 분리하지 못했습니다. 따라서 **정적 집합에서 나온 개선폭은 그대로 믿을 수 없지만, 같은 집합에서 두 조건을 비교하는 것은 여전히 유효합니다.** 절대값이 아니라 차이를 보는 것이기 때문입니다.

L3는 절대값 확인용입니다. "우리 시스템이 몇 %를 푼다"는 문장은 L3에서만 나올 수 있습니다.

### 오염 감사 (R-EVL-2)

CTFusion은 D-cipher에 웹 검색을 추가하자 성공률이 12.59% → 24.07%로 올랐지만, 로그에 **커닝 시도 71건**이 있었고 그중 63건은 flag를 외부에서 그대로 복사한 것이었습니다. 극단적으로는 에이전트가 `nyuctf` 파이썬 패키지를 설치해 벤치마크의 flag에 직접 접근한 사례도 있었습니다.

또한 도구·예산·프로토콜을 완전히 동일하게 두고 **"사전 지식을 쓰지 말라"는 프롬프트만 추가하자 13.6% → 9.7%로 떨어졌습니다**(상대 29% 감소).

그래서 감사는 세 겹입니다.

1. **출처 스캔** — 문제 디렉터리와 도구 출력에서 flag 문자열을 검색한다. `entrypoint.sh`가 기록한 원본 해시로 `/challenge` 무결성을 확인한다
2. **네트워크 회수 검사** — 세션 중 외부에서 가져온 텍스트에 flag가 포함되어 있는지 검사한다
3. **단시간 감사** — `solve_wall_s < fast_solve_threshold_s`면 경로 판정을 강제한다 (BearcatCTF의 CryptoPwn 사례가 이 규칙으로 잡혔습니다)

### 주 지표

| 지표 | 정의 | 왜 필요한가 |
| --- | --- | --- |
| `solve@1`, `solve@3` | 1회·3회 시도 해결률 | 기본 성능. 단독으로는 부족 |
| `consistency` | 3회 중 3회 성공한 문제 수 | 대회에서는 "풀 수 있냐"보다 "안정적으로 푸냐"가 중요 (Second Look의 12→16) |
| `ladder_mean` | 사다리 도달 단계 평균 | 미해결 문제에서 어디까지 갔는지 |
| `cost_per_solve` | 해결당 비용 | 아키텍처의 실측 이득이 여기서 나옴 (−34%) |
| `cle_count` | 컨텍스트 한계 오류 건수 | 요약 계층 실험의 직접 지표 (SIABench에서 0이 됨) |
| `clean_rate` | 감사 통과 비율 | 이것이 낮으면 위 지표 전부가 무의미 |
| `refusal_count` | 도구 호출 전 차단 건수 | 88.2%가 관찰된 조건이 있음 |
| `failure_labels` | 실패 원인 분포 | 무엇이 고쳐졌는지 |

#### X-01 · 요약 계층 on/off

| 항목 | 내용 |
| --- | --- |
| **대상** | `R-CTX-1`, `R-CTX-4` |
| **주장** | 도구 원출력을 파일로 외부화하고 컨텍스트에 요약·포인터만 올리면 컨텍스트 한계 오류가 사라지고 해결률이 오른다 |
| **원 근거** | SIABench **[측정]**: 요약 모듈 제거 시 Claude-3.5-Sonnet이 메모리 포렌식 2건·네트워크 포렌식 3건, GPT-4o가 메모리 포렌식 5건의 CLE 발생. 켜면 CLE **0**, 부분 해결률 +12.5~31.9%p. **단 SOC 사고 분석 과제** |
| **조건 A** | 도구 출력을 그대로 컨텍스트에 넣는다 |
| **조건 B** | `ctfwrap` + 호스트 요약기. 원출력은 `runs/`, 컨텍스트에는 요약 + 파일 포인터 |
| **집합** | L2 전체. 특히 forensic(대용량 아티팩트)과 web의 blind injection 유형 |
| **지표** | `cle_count`(주), `solve@3`, `ladder_mean` |
| **판정** | 조건 B에서 `cle_count`가 유의하게 감소하면 채택. **해결률이 안 올라도 CLE가 줄면 채택합니다** — CLE는 다른 개선을 가리는 노이즈이기 때문 |
| **비고** | 웹의 blind SQLi 실패가 같은 메커니즘이라는 것은 **[가설]**입니다. 이 실험이 그 전이를 함께 검증합니다 |

#### X-03 · 디컴파일러 3조건

| 항목 | 내용 |
| --- | --- |
| **대상** | `R-OBS-3` |
| **주장** | 디컴파일러와 어셈블리를 대등하게 주고 교차 검증시키는 것이, 둘 중 하나만 주는 것보다 낫다 |
| **원 근거** | NDSS BAR 2026 **[측정]**: 디컴파일러 있음 CC 15/24·CX 14/24, 없음 CC **17/24**·CX 14/24. 24문제 중 20문제는 동일, 갈린 4문제 중 3문제(#11·#21·#23)는 제거해야만 풀림. **논문은 "둘 다 주고 교차 검증"이라는 세 번째 조건을 측정하지 않았습니다** |
| **조건 A** | 디컴파일러 우선 (현재 기본 동작) |
| **조건 B** | 어셈블리만 |
| **조건 C** | 둘 다 제공 + 불일치 감지 시 어셈블리 우선 규칙 |
| **집합** | L2의 rev 문제 전체. VM 인터프리터·예외 기반 제어흐름·난독화 문제를 의도적으로 포함 |
| **지표** | `solve@3`, `ladder_mean`, `failure_labels`(W2 관측 과신) |
| **판정** | C가 A·B 모두보다 낫거나 최소한 B와 동등하면 C를 기본값으로. **C가 A보다 못하면 B를 기본값으로 하고 디컴파일러는 탐색 용도로만 씁니다** |
| **비고** | 논문이 답하지 않은 질문을 우리가 답하는 실험입니다. 이 시리즈에서 가장 독자적인 기여가 나올 수 있는 자리 |

#### X-04 · 반증 테스트와 실험 사전 등록

| 항목 | 내용 |
| --- | --- |
| **대상** | `R-ORC-4`, `R-ORC-9`, `R-ORC-10` |
| **주장** | 가설마다 반증 테스트를 붙이고 실험의 유지·폐기 기준을 **실행 전에** 등록하면 W2(관측 과신)와 W4(계획 고착)가 함께 줄어든다 |
| **원 근거** | Failing to Falsify **[측정]**: 반례를 찾도록 유도하자 규칙 발견률 42% → 56% (11개 LLM). **숫자 규칙 과제이며 리버싱·CTF 실험이 아닙니다** |
| **조건 A** | 가설 하나씩, 사후 판단. `falsifier`·`keep_if`·`drop_if` 없음 |
| **조건 B** | 가설 포트폴리오 2~3개 + `falsifier` 필수 + `state.json`의 experiments 필드에 `keep_if`/`drop_if` 사전 등록 |
| **집합** | L2 전체. 특히 rev(오도 단서)와 crypto(패러다임 오인) |
| **지표** | `solve@3`, **가설당 평균 소비 시간**, **폐기까지 걸린 시간**, `failure_labels`(W4 계획 고착 비율) |
| **판정** | 반증 테스트와 사전 등록은 예산을 씁니다. 따라서 **동일 총 예산에서** 판정합니다. W4 라벨 비율이 줄고 `solve@3`이 유지 이상이면 채택 |
| **비고** | 주 지표는 해결률이 아니라 **"틀린 가설을 얼마나 빨리 버리는가"**입니다. 이 엔진의 설계 목표가 그것이기 때문입니다. 도메인 밖 근거에 기반한 설계 중 가장 중요한 항목이고, 효과가 없으면 [엔진 설계도](06-engine-blueprint.md)의 `PLAN_EXPERIMENT` 게이트를 제거합니다 |

#### X-20 · 다중 세션 간섭

> **이 실험은 재정의되었습니다.** 이전 정의는 "대회 계층 순위 정책"(`R-CON-4`~`R-CON-6`)이 총 착지 수를 올리는지를 측정하는 것이었습니다. [구현 설계도](09-implementation-blueprint.md)가 대회 계층 스케줄러를 만들지 않기로 하면서 그 질문은 닫혔습니다. 순위 정책의 우열 대신 **세션을 늘렸을 때 간섭이 생기는가**를 측정합니다.

| 항목 | 내용 |
| --- | --- |
| **대상** | 09 §5.4(자원 리스), Phase 2·4 완료 조건. `R-CON-5`는 폐기, `R-CON-4`·`R-CON-6`은 문제 단위로 축소되어 더 이상 이 실험의 대상이 아닙니다 |
| **주장** | 세션마다 Captain 1 + worker 3의 논리 역할을 유지하면, 세션을 늘려도 각 세션의 풀이 품질이 혼자 돌 때와 유의하게 달라지지 않는다. 간섭 경로에는 tool 예산·GPU·remote rate limit뿐 아니라 provider/account 대기도 포함되며, 대기는 역할을 삭제하거나 wave를 축소하지 않는다 |
| **원 근거** | **직접 근거 없음.** 현재 Batch의 각 `codex exec`는 cross-process FIFO 상한으로 대기시킬 수 있지만 Live native subcall은 CTF-OS가 호출별 lease로 감싸거나 완전히 관측하지 못한다(09 §5.4.3). 간접 근거: Second Look **[측정]** 세 아키텍처 변형이 모두 19/30 — 컴포넌트 수보다 예산이 병목이라는 반대 방향 시사 |
| **조건 A** | 세션 1개. L2 문제 N개를 하나씩 순차로, 각 문제가 전체 예산을 쓴다 |
| **조건 B** | 세션 N개 동시. 각 세션의 논리적 `worker_slots_per_challenge = 3`을 그대로 둔다. Batch model call은 계정 상한의 cross-process FIFO slot을 기다리고, Live 내부 native call은 논리 역할/max-thread 설정만 유지한 채 provider가 실제 시작을 늦출 수 있다 |
| **집합** | L2에서 카테고리 균형으로 N개씩 묶습니다. N = 2, 3. 두 조건의 총 벽시계 예산을 같게 고정합니다(규칙 1) |
| **지표** | 문제별 `solve@3`, `ladder_mean`, `consistency`(주). 부지표로 Batch provider FIFO 대기시간, tool job 큐 대기시간, GPU 대기시간, 429 발생 횟수, 관측 가능한 동시 모델 호출 최대값, `cle_count` |
| **판정** | B의 문제별 분포가 A 대비 유의하게 나빠지지 않으면 채택합니다. 나빠지면 **먼저 어느 층에서 나빠졌는지 가릅니다** — provider FIFO 대기, tool 큐 대기, remote 429를 분리해 측정하고 운영 상한을 조정하되 논리 역할 수는 줄이지 않습니다. 순위 정책으로 되돌아가지 않습니다 |
| **비고** | **총 착지 문제 수를 주 지표로 쓰지 않습니다.** 그걸 주 지표로 쓰면 "스케줄러가 처리량을 올리는가"라는 닫힌 질문으로 되돌아갑니다. 이 실험이 답하는 것은 처리량이 아니라 **간섭의 유무**입니다. 같은 호스트를 쓰는 Web 문제를 둘 이상 넣은 묶음은 제외하지 말고 **별도 조건으로 따로 돌립니다** — remote budget 공유가 간섭을 얼마나 키우는지가 이 실험에서 가장 알고 싶은 값이기 때문입니다 |


단계 번호는 [구현 설계도](09-implementation-blueprint.md) §16의 Phase 0~7을 따릅니다. 이전 판의 1~8단계 번호와는 다릅니다 — Phase 0(Doctor)이 앞에 생기고, 대회 스케줄러 단계가 사라진 자리에 자원 리스가 Phase 2로 앞당겨졌습니다.

**별표 여섯 개가 이 백로그의 핵심이고, 09 §17의 우선순위와 같습니다.**

1. `X-01` 출력 외부화 — 근거가 가장 강하므로 재현되는지 먼저 확인합니다
2. `X-02` 순차 목표 처리 — SOC에서 45.9% → 70.0%. CTF 전이 폭을 확인합니다
3. `X-19` 독립 Falsifier — 반증을 별도 역할로 분리한 결정을 정당화합니다. 기각되면 설계가 단순해집니다
4. `X-16` 관측성·진전 마커 — 정체 판정과 복구의 입력이므로 이게 없으면 Phase 4가 근거 없이 돕니다
5. `X-03` 디컴파일러 3조건 — 원 논문이 답하지 않은 세 번째 조건이므로 독자적 기여가 나올 수 있습니다
6. `X-20` 다중 세션 간섭 — 순위 로직 없이 리스만으로 충분하다는 09의 결론을 검증합니다

별표가 아니지만 빼면 안 되는 셋도 적어둡니다. `X-18`은 실행기 설계를 바꿀 수 있어 Phase 1과 동시에 돌립니다. `X-04`는 도메인 밖 근거로 도입된 설계라 검증 없이 유지하면 안 됩니다. `X-17`은 이 설계도 전체가 Second Look의 함정(정교화해도 천장은 안 오름)에 빠졌는지를 판정합니다.

**곡선 측정이 별도 단계에서 사라진 것**이 이전 판에서 바뀐 부분입니다. `codex exec --json`의 `turn.completed.usage`와 `turn.failed`가 토큰 사용량과 거부를 이미 주므로, Phase 1에서 이벤트 스트림을 적재하면 Phase 3~5 실행이 곡선 데이터를 부산물로 쌓습니다. Phase 7의 평가가 그걸 읽습니다. 09에서 이 곡선은 예산을 자동 배정하는 입력이 아니라 board에 표시되는 운영 판단 재료입니다.

**돌리지 않을 실험도 명시합니다.** `X-15`(궤적 인계)는 근거가 전무하므로 기능으로 만들지 않고, 다른 실험이 끝난 뒤 여유가 있을 때만 봅니다.

실험 결과는 `ctf-reports/experiments/X-NN.md`에 다음 형식으로 남깁니다. 형식을 고정하는 이유는, 결과가 흩어지면 6개월 뒤에 "이거 측정했었나?"를 다시 묻게 되기 때문입니다.

```markdown
# X-01 · 요약 계층 on/off
```
