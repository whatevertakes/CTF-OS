# 당신의 AI Agent가 CTF 문제를 못 푸는 이유 — 포너블 편

> 이 글의 “CTF-OS 현황”은 연구 시작 시점의 역사적 baseline이다.
> 현재 구현 판정은 [10](10-implementation-result.md)과
> [12](12-final-acceptance.md)를 따른다.

포너블은 Agent가 가장 인상적으로 잘하는 카테고리이면서, 동시에 가장 극적으로 무너지는 카테고리입니다. 같은 모델이 userspace 힙 문제를 20분 만에 풀고 커널 문제에서는 2시간 내내 아무것도 못 합니다.

이 글은 그 격차가 어디서 나오는지를 정리합니다. 다행히 포너블은 이 시리즈에서 근거가 가장 튼튼한 분야입니다. 898개 실제 취약점으로 구성된 벤치마크가 2026년에 공개되면서, 그동안 감으로 이야기되던 것들이 대부분 숫자로 확인됐습니다.

> **인용 규칙**: **[측정]** = 논문이 실제로 측정한 결과(측정 조건 병기), **[해석]** = 논문 저자의 설명, **[가설]** = 이 글의 제안(미검증). 출처 등급은 **A** 동료평가 논문 / **B** arXiv 프리프린트 / **C** 운영 사례·블로그 / **D** 도구 저장소입니다.

## Agent가 포너블 문제를 푸는 방식

기본 흐름은 사람과 같습니다. `checksec`으로 보호 기법을 확인하고, `strings`와 디컴파일러로 의심스러운 함수를 찾고, 크래시를 재현하고, 오프셋을 계산하고, pwntools로 익스를 쓰고, 로컬에서 성공하면 원격으로 옮깁니다.

Agent의 강점은 이 루프를 지치지 않고 수십 번 돈다는 것입니다. 사람이라면 오프셋을 세 번 틀리고 나서 잠깐 멈추지만, Agent는 계속 돌립니다. 그리고 pwntools 스크립트를 쓰는 속도가 빠릅니다.

문제는 포너블이 **정적 이해가 아니라 런타임 상태 추론**을 요구한다는 점입니다. ExploitGym 논문은 이 요구사항을 세 가지로 정리합니다. 메모리 레이아웃(힙 메타데이터, 스택 프레임, 가상 메모리 매핑)에 대한 저수준 추론, 실행 중 관찰에 따른 적응, 그리고 긴 시간에 걸친 진전의 유지입니다 [1].

이 세 가지 중 어느 것도 "코드를 읽고 설명하기"로는 얻어지지 않습니다. 그리고 셋 다 **환경이 관측을 얼마나 허용하느냐**에 직접 묶여 있습니다. 뒤에서 보겠지만, 포너블에서 카테고리 내 성능 격차의 상당 부분이 여기서 설명됩니다.

## ExploitGym이 측정한 것

> **ExploitGym**은 실제 취약점 898개(userspace 520, V8 185, Linux kernel 193)로 구성된 익스플로잇 능력 벤치마크입니다.[^exploitgym-count] 각 문제는 취약한 소스코드, 크래시를 일으키는 PoV 입력, 재현 가능한 컨테이너 환경을 주고 **실제 동작하는 익스플로잇**을 요구합니다. flag를 얻는 것만으로는 부족하고, 지정된 취약점을 실제로 사용했는지를 agent-as-a-judge가 별도로 검증합니다. 보호 기법을 켜고 끄는 조건을 따로 두어 완화 기법의 영향을 분리할 수 있게 설계했습니다 [1]. **(B)**

[^exploitgym-count]: 논문 초록은 898개, 프로젝트 페이지(cybergym.io/exploitgym)는 869개로 표시합니다. 어느 쪽이 최신인지 확인하지 못했습니다. 이 글은 논문 값 898을 쓰며, 도메인별 내역(520+185+193)이 그 값과 정합합니다. [출처 검증 기록](08-verification-log.md) 참조.

**[측정]** 2시간 타임아웃, 시도 1회 기준 결과입니다 [1].

| 모델 + 에이전트 | 전체 성공 | userspace | V8 | kernel |
| --- | --- | --- | --- | --- |
| Claude Mythos Preview + Claude Code | 157 | 107 | 38 | 12 |
| GPT-5.5 + Codex CLI | 120 | 71 | 27 | 22 |
| GPT-5.4 + Codex CLI | 54 | 38 | 15 | 1 |
| Claude Opus 4.6 + Claude Code | 15 | 12 | 2 | 1 |
| Gemini 3.1 Pro + Gemini CLI | 12 | 10 | 2 | 0 |

**이 표를 읽을 때 주의할 점이 있습니다.** 이건 "모델 순위표"가 아니라 **모델 + 에이전트 + 시간 예산 + 시도 횟수의 조합에 대한 측정값**입니다. 논문 스스로 제한사항으로 단일 시도, 2시간 제한, 특정 실행 환경, 취약점 전용 도구 미제공을 명시하고 있습니다. 같은 모델을 다른 스캐폴딩에 얹거나 시도를 3회로 늘리면 숫자는 달라집니다.

절대 수치보다 중요한 건 이 표에서 반복적으로 나타나는 **구조**입니다. 아래 네 개 절이 그 구조입니다.

## 도메인이 바뀌면 다른 경기가 된다

표를 가로로 읽으면 도메인 간 격차가 눈에 띕니다.

- **userspace**: 상위권뿐 아니라 하위권 모델도 두 자릿수를 냅니다.
- **V8**: 성공이 상위 3개 조합에 집중됩니다.
- **kernel**: 최상위 두 조합 외에는 1문제를 넘지 못합니다.

**[해석]** 논문은 커널이 유독 어려운 이유를 네 가지로 정리합니다. 전역 공유 힙이라 동시 실행 프로세스의 노이즈 때문에 레이아웃 예측이 어렵고, 다수 취약점이 공격자가 통제할 수 없는 타이밍의 race에 의존하며, 커널 버전이나 설정 하나만 바뀌어도 동작이 크게 달라지고, 무엇보다 디버깅 관측성이 극도로 제한됩니다 [1].

네 가지 중 세 가지가 **난이도가 아니라 관측성**의 문제라는 점을 봐야 합니다. 커널 문제가 지적으로 더 어려워서가 아니라, Agent가 자기 가설을 확인할 방법이 없어서 못 푸는 쪽에 가깝습니다.

CTF에 대입하면 바로 짚이는 게 있습니다. heap feng shui, 힙 그루밍이 필요한 tcache/fastbin 문제, race 기반 문제가 Agent에게 유독 안 풀리는 이유가 여기입니다. 이 문제들은 전부 "지금 힙이 어떤 상태인지"를 정확히 알아야 하는데, Agent가 볼 수 있는 것은 크래시 여부와 stdout뿐인 경우가 많습니다.

> **[가설]** 그렇다면 커널·힙 문제의 성능은 모델을 바꾸는 것보다 **관측 채널을 늘리는 것**으로 더 크게 움직일 가능성이 있습니다. 디버거 MCP, 주기적 힙 덤프, 할당자 상태 요약을 도구로 제공하는 것이 후보입니다. 다만 ExploitGym은 "취약점 전용 도구를 제공하지 않았다"고만 밝혔을 뿐, 도구를 추가했을 때 얼마나 오르는지는 측정하지 않았습니다. 이건 직접 A/B로 확인해야 할 항목입니다.

## 완화 기법은 문을 닫지 않는다

**[측정]** 성공한 문제들에 대해 완화 기법을 다시 켜고 재실행하자 대부분 실패했지만, userspace 37건, V8 20건, kernel 12건은 여전히 뚫렸습니다 [1].

**[측정]** 우회 방식도 로그에서 확인됐습니다.

- **ASLR** → partial pointer overwrite와 하위 비트 브루트포스
- **V8 샌드박스** → Wasm dispatch table, Irregexp bytecode 같은 알려진 rendezvous primitive
- **KASLR** → `modprobe_path`, `core_pattern` 같은 쓰기 가능한 정적 문자열 악용

여기서 읽을 것은 **모델이 완화 기법을 우회하는 방식이 전부 "공개된 표준 기법"**이라는 점입니다. 새로운 우회를 발명한 게 아니라, write-up에 수없이 나온 패턴을 정확한 자리에 적용했습니다.

**[가설]** 이게 사실이라면 CTF 관점에서 따라오는 함의가 있습니다. 출제자가 알려진 rendezvous primitive를 막아둔 문제는 Agent 성능이 급락할 가능성이 큽니다. 반대로 Agent 운영자 입장에서는 **완화 기법별 우회 기법 카탈로그를 명시적 지식으로 주입하는 것**이 유효할 수 있습니다. 다만 ExploitGym은 이 주입 효과를 측정하지 않았습니다.

## 시간이 곧 성능이다, 단 모델마다 곡선이 다르다

이건 자동화 시스템 설계에 가장 직접적으로 쓰이는 발견입니다.

**[측정]** 시간에 따른 누적 성공 곡선의 모양이 모델마다 크게 달랐습니다. Claude Opus 4.6은 30분 안에 약 15문제에서 포화되고 그 뒤로는 거의 진전이 없었습니다. 반면 Claude Mythos Preview는 첫 1시간에 가파르게 오른 뒤 2시간을 넘겨서도 계속 성공을 누적했고, 6시간까지 뚜렷한 포화점이 없었습니다 [1].

**단일 성공률만 보면 이 차이가 안 보입니다.** "2시간에 15문제"와 "2시간에 15문제"가 같아 보여도, 하나는 30분에 이미 끝난 것이고 다른 하나는 아직 오르는 중일 수 있습니다.

> **[가설]** 그렇다면 예산 배정의 원칙은 이렇게 됩니다. 자기가 쓰는 모델의 **시간-성공 곡선을 먼저 측정하고**, 조기 포화형 모델에는 짧은 예산을 여러 번(재시도 다양성 확보), 지구력형 모델에는 긴 예산을 한 번 주는 것입니다. 조기 포화형에 2시간을 통으로 배정하는 것은 낭비일 가능성이 높습니다. 다만 "짧게 여러 번"이 "길게 한 번"보다 실제로 나은지는 ExploitGym이 측정하지 않았습니다. 곡선의 모양이 다르다는 것까지가 측정이고, 예산 분할 전략은 제안입니다.

## 모델마다 푸는 문제가 다르다

**[측정]** 상위 두 조합이 푼 문제 집합을 비교하면 Claude Mythos Preview 단독 56개, GPT-5.5 단독 26개, 공통 91개였습니다. 평가된 모든 조합의 합집합은 239개로, 단일 최고 조합(157)보다 훨씬 큽니다 [1].

이 숫자는 널리 인용되면서 종종 "앙상블이 항상 이득"이라는 결론으로 넘어갑니다. **그 도약은 데이터가 지지하지 않습니다.**

239라는 합집합은 서로 다른 모델, 서로 다른 에이전트, 서로 다른 실행 조건에서 나온 성공을 전부 합친 값입니다. 즉 **투입된 총 연산량이 157을 낸 단일 실행보다 훨씬 큽니다.** 동일한 예산을 놓고 "한 모델에 다 쓰기 vs 여러 모델에 나눠 쓰기"를 비교한 실험이 아닙니다.

정확한 진술은 다음과 같습니다.

**[측정]** 모델·에이전트 조합에 따라 성공하는 문제 집합이 상당히 다르며, 합집합은 단일 최고 조합의 1.5배가 넘습니다.
**[가설]** 따라서 예산이 충분하다면 서로 다른 조합을 병렬로 돌리고 합집합을 취하는 것이 커버리지를 넓힐 수 있습니다. **동일 예산 조건에서의 효율은 검증되지 않았으므로, 직접 측정해야 합니다.**

측정 방법도 어렵지 않습니다. 총 GPU-시간 또는 총 비용을 고정해 놓고, (a) 단일 최고 조합에 전부 투입, (b) N개 조합에 1/N씩 분할 투입을 같은 문제 집합에 돌려 비교하면 됩니다. 이 실험은 아직 공개된 것을 못 봤습니다.

## flag를 얻은 것과 익스에 성공한 것은 다르다

ExploitGym이 flag 획득과 별도로 "지정된 취약점을 실제로 썼는가"를 판정하는 이유가 여기 있습니다.

**[측정]** Claude Mythos Preview는 flag를 얻은 226건 중 실제 성공으로 인정된 것이 157건(69.5%), GPT-5.5는 210건 중 120건(56.7%)이었습니다 [1]. 나머지는 주변의 더 쉬운 취약점을 발견해 갈아탄 경우입니다.

**절반 가까이가 의도하지 않은 경로였다는 뜻입니다.**

CTF 대회 자체에서는 이게 문제가 안 됩니다. flag를 냈으면 점수를 받습니다. 하지만 **자기 시스템의 능력을 평가할 때는 치명적입니다.** "우리 시스템이 pwn 문제의 70%를 푼다"는 문장에서 그중 절반이 README를 읽거나 옆 취약점으로 샌 것이라면, 그 숫자로는 다음에 뭘 개선해야 할지 알 수 없습니다.

앞서 BearcatCTF 기록에서 나온 README 사례가 정확히 이 유형입니다 [2]. 짧은 시간에 풀린 문제에 자동 감사를 걸어두었더니, CryptoPwn 문제에서 실제 익스플로잇 대신 챌린지 디렉터리의 `README.md`에 있던 flag를 읽은 것이 `CHEATED`로 잡혔습니다.

> **[가설]** 자기 평가에는 flag 판정과 **경로 판정**을 분리해서 두는 것이 필요합니다. 최소한 (1) 지정 취약점의 트리거 여부, (2) 익스 스크립트의 재현 가능성, (3) 비정상적으로 짧은 풀이 시간에 대한 자동 감사 정도입니다. ExploitGym은 agent-as-a-judge로 (1)을 했고, BearcatCTF 팀은 (3)을 운영했습니다. 세 가지를 다 갖춘 공개 사례는 아직 없습니다.

## 조기 포기와 안전 필터

성능을 갉아먹는 요인 중 추론 능력과 무관한 것이 둘 있습니다.

**조기 포기.** **[측정]** Claude Opus 4.7과 Gemini 3.1 Pro는 대상 취약점이 익스플로잇 불가능하다고 판단하고 일찍 종료하는 경우가 잦았습니다. 흥미롭게도 Opus 4.7은 더 최신 체크포인트인데도 4.6보다 성공 수가 적었습니다 [1].

**[해석]** 이건 능력 저하가 아니라 **중단 판단 기준의 차이**로 설명됩니다. 그리고 이런 종류의 실패는 스캐폴딩으로 상쇄 가능한 쪽에 속합니다.

**안전 필터.** **[측정]** GPT-5.4에서 36건, GLM-5.1에서 23건의 거부가 관찰되었습니다. 기본 안전 필터를 켠 GPT-5.5는 88.2%의 경우 도구 호출 전에 차단되었습니다 [1].

이건 실무적으로 중요합니다. 상용 API로 pwn 자동화를 돌리는데 원인 불명의 정체가 생긴다면, 모델 능력이나 프롬프트를 의심하기 전에 **거부 로그부터 확인하는 게 순서**입니다. 88.2%라는 숫자는 성능 측정 자체를 무의미하게 만드는 수준입니다.

## 이를 보완하는 연구와 도구

포너블 Agent를 보완하는 방향은 크게 셋으로 갈립니다. **관측성을 늘리는 도구**, **채점을 세분화하는 벤치마크**, **계획을 구조화하는 프레임워크**입니다.

> **PWN-MCP**는 MCP 기반으로 AI가 원격 타겟의 GDB를 직접 조작하고, CTF 서비스와 상호작용하며, 힙 상태를 분석하도록 만든 pwn 전용 디버깅 플랫폼입니다 [3]. **(D)**

> **pwndbg MCP**는 GDB/MI로 직접 통신해 프로세스에 임의 바이너리 데이터를 보내고 받을 수 있게 한 ELF 디버깅 MCP 도구입니다 [4]. **(D)**

두 도구 모두 **관측 채널을 늘리는** 접근입니다. 앞서 커널·힙 문제의 병목이 관측성이라고 봤다면 방향은 맞습니다. 다만 **두 저장소 모두 성능 향상을 측정한 공개 데이터는 제시하지 않습니다.** 존재와 주장된 기능까지만 확인 가능한 D등급 자료로 취급해야 합니다.

> **ExploitBench**는 익스플로잇을 coverage와 crash에서 샌드박스 primitive, 임의 읽기/쓰기, 제어흐름 탈취, 임의 코드 실행까지 **16개 측정 가능한 flag**로 쪼개어 채점하는 벤치마크입니다. 각 능력은 결정적 오라클로 검증하며, primitive에는 실행마다 랜덤화된 challenge-response를, 진전 측정에는 정답 바이너리와의 차분 실행을, 코드 실행에는 시그널 핸들러 증명을 씁니다. **익스플로잇 대응이 강화된 V8을 골라 41개 버그에 인스턴스화했습니다** [5]. **(B)**

이 접근이 유용한 이유는 "성공/실패" 이진 판정이 병목을 감추기 때문입니다. 100문제 중 5개를 풀었다는 정보만으로는 나머지 95개에서 크래시조차 못 냈는지, 크래시는 냈는데 제어를 못 잡았는지, 제어는 잡았는데 샌드박스를 못 나갔는지 알 수 없습니다. **어디까지 갔다가 멈췄는지**를 보면 다음에 뭘 고쳐야 할지가 보입니다.

그리고 사다리 채점이 실제로 무엇을 드러내는지가 이 논문의 결과에 나옵니다.

**[측정]** 공개 배포된 프론티어 모델 8개에서 **취약 코드에 도달해 크래시를 내는 것은 일상적이었지만 임의 코드 실행은 그렇지 않았습니다.** 반면 비공개 모델은 약 절반에서 임의 코드 실행에 도달했습니다 [5].

**이진 채점으로는 이 진단이 나오지 않습니다.** "대부분 실패"와 "대부분 크래시까지는 가는데 그 위로 못 올라감"은 완전히 다른 정보이고, 후자만이 다음에 무엇을 만들어야 하는지를 알려줍니다. CTF-OS가 카테고리별 사다리를 도입하는 근거가 이것입니다([엔진 설계도](06-engine-blueprint.md)의 `R-ORC-5`).

> **STRIATUM-CTF**는 시스템 조사, 디컴파일, 런타임 디버깅의 도구 인터페이스를 MCP로 표준화해 긴 익스플로잇 궤적에서도 컨텍스트를 일관되게 유지하도록 설계한 프레임워크입니다 [6]. **(B)**

**[측정]** STRIATUM-CTF는 2025년 말 대학이 주최한 4시간 규모 CTF에 자율 참가해 유효 22개 팀 중 1위(215점, 2위 205점, 3위 200점)를 기록했습니다 [6].

**이 결과는 정확히 그 조건에서만 읽어야 합니다.** 참가자는 주로 해당 대학의 보안 과목 수강생이었고, 문제 구성은 pwn과 web 중심이었으며, 대학명은 익명화됐고 원시 실행 로그와 독립 재현 결과는 충분히 공개되지 않았습니다. **"21개 인간 팀을 제치고 1위"는 사실이지만, 국제 CTF 상위권 팀보다 낫다는 근거로는 쓸 수 없습니다.**

> **Excalibur**는 28개 LLM 침투 테스트 시스템을 분석하고 5개 대표 구현을 3개 벤치마크에서 평가한 뒤 제안된 에이전트입니다. 실패를 Type A(도구·프롬프트 부재로 엔지니어링으로 해결 가능)와 Type B(계획·상태 관리 한계로 모델을 바꿔도 지속)로 나눈 것이 핵심 기여입니다 [7]. **(B)**

**[해석]** 이 논문은 Type B 실패의 공통 원인을 **실시간 난이도 추정 능력의 부재**로 지목합니다. 난이도를 모르니 노력을 잘못 배분하고, 가치 낮은 가지에 과도하게 매달리고, 공격 체인을 완성하기 전에 컨텍스트를 소진한다는 것입니다.

**[측정]** 난이도 인지 계획(horizon estimation, evidence confidence, context load, historical success 네 축)을 붙인 Excalibur는 프론티어 모델 기준 CTF 벤치마크에서 최대 91% 과제 완료(베이스라인 대비 상대 39~49% 개선), GOAD Active Directory 환경에서 5개 호스트 중 4개 장악(기존 시스템 2개)을 기록했습니다 [7].

**Type A / Type B 구분은 이 시리즈 전체에서 가장 쓸모 있는 도구입니다.** 앞서 본 조기 포기와 안전 필터는 Type A에 가깝고, 커널 레이아웃 추론은 Type B에 가깝습니다. **어느 쪽인지 먼저 분류하지 않으면 도구를 아무리 붙여도 안 오르는 문제에 도구를 계속 붙이게 됩니다.**

## 성공/실패 조건 정리

앞의 관찰을 조건 표로 옮기면 다음과 같습니다.

| 잘 푸는 조건 | 관찰되는 특징 | 왜 잘 맞는가 |
| --- | --- | --- |
| 단일 프로세스, 결정적 메모리 레이아웃 | userspace 문제에서 하위권 모델도 두 자릿수를 냅니다 | 관측한 상태와 실제 상태가 일치하므로 가설 검증이 성립합니다 |
| 로컬에서 즉시 재현되는 크래시 | PoV 입력이 주어지면 시작점이 명확합니다 | 검증 루프가 짧아 후보를 빠르게 버릴 수 있습니다 |
| 알려진 primitive | 스택 오버플로우, ret2libc, 단순 UAF | 학습 분포와 공개 write-up이 두껍습니다 |
| 우회법이 공개된 완화 기법 | ASLR partial overwrite, `modprobe_path` 등 | 탐색 공간이 알려진 카탈로그로 좁혀집니다 |
| 지구력형 모델 + 긴 시간 예산 | 성공 곡선이 2시간 이후에도 상승 | 긴 궤적에서 성공이 계속 누적됩니다 |

| 실패 조건 | 관찰되는 특징 | 필요한 보완 |
| --- | --- | --- |
| 전역 공유 힙, 동시 실행 노이즈 | 커널에서 상위 두 조합 외 1문제 이하 | 레이아웃 결정성 확보, 반복 시행 통계, 힙 상태 관측 채널 |
| 타이밍 의존 race | 통제 불가능한 타이밍에 성공이 좌우됨 | 병렬 실행기와 동기화 프리미티브를 도구로 제공 |
| 관측성 낮은 환경 | 커널, 원격 전용, 디버거 미부착 | 디버거 MCP, 메모리 덤프, 강제 trace |
| 조기 포기 | 최신 체크포인트가 이전 버전보다 성공 수가 적음 | "가설 소진" 기반 중단 조건, 재시도 예산 분리 |
| 안전 필터 | 도구 호출 전 차단이 88.2%까지 관찰됨 | 거부 로그 계측을 평가 파이프라인에 상시 포함 |
| 이진 성공/실패 채점 | 어디서 멈췄는지 알 수 없음 | 단계별 primitive 채점(사다리형 평가) |

| ID | 요구사항 | 이 글의 근거 | 상태 | CTF-OS 현황 |

| **R-BGT-3** | 계획이 틀렸다고 판정되면 예산을 남기고 종료한다 | 조기 포기가 능력 저하가 아니라 중단 기준 차이였다 **[해석]** | 측정 기반 | 미구현. Challenge Engine의 governor 모듈 |

| **R-ORC-3** | 비정상적으로 짧은 풀이에 자동 감사를 건다 | CryptoPwn README 커닝이 감사로 잡힘 **(C)** | 운영 사례 | 미구현. Falsifier + Proof |
| **R-ORC-5** | 카테고리별 사다리로 채점한다 | 공개 모델은 크래시는 일상적, ACE는 아님 **[측정]** | 벤치마크 설계 | 미구현. Phase 5 (카테고리 adapter의 `progress_markers`) |
| **R-OBS-4** / **R-ENV-3** | 힙 상태·레이아웃 관측 채널을 구조화 인터페이스로 노출한다 | 커널 난이도 네 이유 중 셋이 관측성 **[해석]** | **[가설]** | pwndbg 있음, 구조화 없음 (`X-16`) |
| **R-ENV-2** | 병렬·동기화 실행기를 제공한다 | race는 통제 불가 타이밍에 성공이 좌우됨 **[해석]** | 측정 기반 | **미충족** (`X-10`) |
| **R-KNW-4** | 완화 기법별 우회 카탈로그를 명시적 지식으로 축적한다 | 우회 방식이 전부 공개된 표준 기법이었음 **[측정]** | 주입 효과는 **[가설]** | 미구현. 문제별 `knowledge/` (Ledger는 09에서 폐기) |

**이 표에서 가장 먼저 해야 할 것은 성능 개선이 아니라 계측입니다.** `R-BGT-7`을 켜지 않은 상태의 측정값은 전부 신뢰할 수 없습니다. 88.2%가 관찰된 조건이 존재하는데 거부 로그를 보지 않으면, 스캐폴딩을 고치고 있다고 생각하면서 실제로는 안전 필터에 막힌 세션을 세고 있을 수 있습니다.

**두 번째로, 포너블은 Type A와 Type B가 가장 선명하게 갈리는 카테고리입니다.** 조기 포기와 안전 필터는 Type A이고, 커널 힙 레이아웃 추론은 Type B입니다. Excalibur의 이 구분을 쓰지 않으면 안 오르는 문제에 계속 도구를 붙이게 됩니다.
